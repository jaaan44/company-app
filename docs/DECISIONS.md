# DECISIONS — Architectural & Product Decision Ledger

Durable record of accepted decisions. Each entry is permanent once recorded — a superseded decision is marked `SUPERSEDED` and links to its replacement; it is never deleted or silently rewritten. New decisions get new, incrementing IDs.

---

### DEC-001 — Repository-based development memory
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** Repository documentation is authoritative for project state. Conversation history is not authoritative.
**Rationale:** Enables reliable recovery of project state across sessions, developers, and AI context resets without dependency on chat history.

### DEC-002 — Phase-based development
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** Development proceeds through explicitly authorized phases. A phase must be completed, reviewed, and tested as appropriate, and approved before the next phase begins.
**Rationale:** Prevents scope creep and uncontrolled speculative implementation; keeps each unit of work reviewable.

### DEC-003 — Laravel + Flutter architecture
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** Laravel provides the backend/API and the Admin Backoffice. Flutter provides the staff mobile application.
**Rationale:** Given technology direction for the project; Laravel's ecosystem covers API + admin web needs, Flutter covers cross-platform mobile with a single codebase.

### DEC-004 — Granular authorization
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** Authorization is permission-oriented rather than relying solely on hard-coded role checks.
**Rationale:** Roles alone don't scale to the operational nuance the product needs (e.g. a Supervisor's data visibility vs. an Administrator's). Permissions as the primitive, roles as bundles, keeps this flexible.

### DEC-005 — Location model
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** V1 favors explicit employee location/check-ins instead of continuous GPS tracking. Continuous tracking is outside the initial product direction.
**Rationale:** Simpler, more private, and sufficient for the intended use cases (client visit confirmation, field presence) without the privacy/battery/infrastructure burden of continuous tracking.

### DEC-006 — Tasks may exist independently
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** Tasks may optionally belong to a project. Internal company tasks must be possible without creating artificial projects.
**Rationale:** Forcing every task into a project would create noise (fake "Internal" projects) and misrepresent the data model.

### DEC-007 — Simple messaging first
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** The initial messaging system remains lightweight. Do not attempt to reproduce Slack/Teams functionality in V1.
**Rationale:** Messaging is a supporting feature of an operations platform, not the product's core value; scope discipline avoids an open-ended chat-platform build.

### DEC-008 — Connected domain model
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** Modules should not become isolated mini-applications. Staff, clients, projects, tasks, work logs, schedules, service reports, and incidents should have meaningful relationships where appropriate.
**Rationale:** Preserves the value of a unified operations platform over a collection of disconnected tools; supports reporting and cross-module workflows.

### DEC-009 — Auditability
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** Important administrative and workflow actions should eventually have auditable histories.
**Rationale:** Required for accountability in an internal operations tool handling HR, incident, and administrative data.

### DEC-010 — Historical operational records
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** Important state changes such as staff status, leave approvals, and incident progress should preserve history where appropriate rather than simply overwriting previous state.
**Rationale:** Operational and compliance value in knowing not just current state but how it got there; supports reporting and dispute resolution.

### DEC-011 — Monorepo structure: apps/api and apps/mobile
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** Company App is developed as a single monorepo. The Laravel backend/API (and, eventually, the Admin Backoffice) lives under `apps/api`; the Flutter staff mobile app lives under `apps/mobile`. No monorepo orchestration tooling (Nx/Turborepo/Melos) is introduced — the two applications operate independently within the shared repository.
**Rationale:** Resolves the "monorepo vs polyrepo" open question from `02_ARCHITECTURE.md` §9 in favor of the suggested default, appropriate for a single team with tightly coupled release cadence at ~100-user scale. This decision fixes *structure and location* only — it does not decide the Admin Backoffice's rendering approach (Blade/Livewire/Inertia/SPA), which remains open.

### DEC-012 — Local bootstrap database: SQLite, production engine still open
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** The Laravel application's local development bootstrap uses SQLite (Laravel's own default for a fresh install). This is a local/dev convenience only. It does **not** resolve the PostgreSQL vs. MySQL open question recorded in `02_ARCHITECTURE.md` §9 for production — that choice remains deliberately open until a phase that genuinely requires it.
**Rationale:** Avoids silently converting an intentionally deferred architecture decision into a permanent one merely because a bootstrap step needed *some* working database driver. SQLite requires no separate service, matching the resource-efficiency direction for Phase 1.
**Update (2026-09-10):** the production engine question this decision left open is now resolved — see DEC-016 (MySQL). This entry's own content (SQLite for local/test use) is unchanged and still accurate.

### DEC-013 — No Docker by default for local development
**Date:** 2026-09-09
**Status:** SUPERSEDED by DEC-027
**Decision:** Company App's default local development workflow does not use Docker. PHP, Composer, Node.js, and the Flutter SDK installed directly on the developer's machine are sufficient and are what both apps have actually been built and validated against (Phases 1–2).
**Rationale:** At ~100 users, an always-running container layer adds idle resource overhead and setup complexity with no demonstrated need — both apps run cleanly without it. This does not forbid Docker later for a specific, demonstrated need (e.g. standardizing a chosen non-SQLite database across contributors); it only sets the default.

### DEC-014 — Static analysis: Larastan v3, level 5
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** Backend static analysis uses Larastan (PHPStan for Laravel) v3, configured at `apps/api/phpstan.neon` scanning `app/` at level 5, with no ignored-error baseline.
**Rationale:** Level 5 is a realistic, moderate starting point for a currently near-empty codebase — strict enough to catch real classes of bugs, not so strict (e.g. max/9) that it would demand suppression rules or fight Eloquent's dynamic behavior before any real business logic exists. The level should be raised deliberately as the codebase matures, not lowered to make a failing check pass.

### DEC-015 — CI layout: two path-filtered GitHub Actions workflows
**Date:** 2026-09-09
**Status:** ACCEPTED
**Decision:** CI is two separate workflow files — `.github/workflows/backend-ci.yml` and `.github/workflows/mobile-ci.yml` — each triggered on pull requests targeting `main` and pushes to `main`, and each scoped via `paths:` to its own app directory (plus its own workflow file) so an unrelated app's changes don't trigger it. Single PHP version (8.4) and single Flutter version (3.47.2); no build matrix; no Android/iOS artifact builds.
**Rationale:** Matches the resource-efficiency direction (`02_ARCHITECTURE.md` §0) — fast, cheap CI appropriate for a ~100-user internal tool. Two small workflows were chosen over one workflow with two jobs for clearer independent history/status per app, without adding real complexity (no shared logic between them to justify combining).

### DEC-016 — Production database: MySQL
**Date:** 2026-09-10
**Status:** ACCEPTED
**Decision:** MySQL is the intended production relational database for Company App. This closes the PostgreSQL-vs-MySQL open question left by DEC-012 for production use. SQLite continues to be used for lightweight local development and automated tests where behavior is database-neutral. No production database server is provisioned by this decision — it records direction only.
**Rationale:** A single, well-understood, conventional choice appropriate for a ~100-user internal Laravel application; avoids carrying an open question indefinitely once the phase authorized to close it did so. DEC-012's original content (SQLite for local bootstrap) remains accurate and is not rewritten — this decision only resolves what DEC-012 explicitly left open.

### DEC-017 — Identifier strategy: numeric internal ID + ULID public ID
**Date:** 2026-09-10
**Status:** ACCEPTED
**Decision:** Internal relational primary keys remain auto-incrementing unsigned `BIGINT` (Laravel's `$table->id()`), used for foreign keys and internal joins. Externally addressable business entities (APIs, URLs, mobile references) additionally carry a `ULID public_id` column (`$table->ulid('public_id')->unique()`) once such an entity is actually built. Not every table needs one — pivot/history tables generally don't; user-facing entities (Staff, Clients, Projects, Tasks, Leave Requests, Service Reports, Incidents) likely will. Each future phase decides per entity rather than applying this blindly everywhere.
**Rationale:** Numeric PKs keep joins/indexes fast and simple; ULIDs avoid exposing predictable sequential IDs externally and sort chronologically (useful for pagination/ordering) unlike random UUIDv4. Resolves the "UUID vs auto-increment" open question from `03_DATABASE_MODEL.md` §3. No business migrations were created to demonstrate this — it is a documented convention for future phases to apply when they build real entities.

### DEC-018 — Laravel application architecture: modular monolith, conventional structure
**Date:** 2026-09-10
**Status:** ACCEPTED
**Decision:** Company App's backend remains a single Laravel application (no microservices, no independently deployable modules). Future modules are organized through standard Laravel conventions — Controllers (thin), Form Requests (validation), Policies (authorization), Models/Eloquent (no repository pattern), Action/Service classes only where business logic genuinely warrants extraction, Jobs for genuinely asynchronous/expensive work, Events/Listeners only for meaningful decoupling. No empty directories or placeholder classes are created for modules that don't exist yet.
**Rationale:** Matches the resource-efficiency direction (`02_ARCHITECTURE.md` §0) and avoids premature abstraction (repository pattern, service-layer-for-everything) that adds indirection without a demonstrated need at this scale.

### DEC-019 — Admin Backoffice: Laravel Blade + Livewire
**Date:** 2026-09-10
**Status:** ACCEPTED
**Decision:** The future Admin Backoffice will be built with Laravel Blade + Livewire, inside `apps/api` (per DEC-011's location decision). No separate React/Vue/Inertia SPA. `livewire/livewire` (^4.4) is installed as of this phase; no Admin pages, dashboard, or business CRUD screens are built yet.
**Rationale:** Reduces frontend duplication and toolchain surface for an internal, ~100-user system built primarily around forms, CRUD, and dashboards — Livewire lets the same Laravel application/team produce the Admin UI without a separate frontend build pipeline, consistent with the resource-efficiency direction. This resolves the "Admin Backoffice implementation style" open question from `02_ARCHITECTURE.md` §9.

### DEC-020 — API foundation: versioned REST at /api/v1, response conventions implemented
**Date:** 2026-09-10
**Status:** ACCEPTED
**Decision:** The API is rooted at `/api/v1` (`routes/api.php` → `routes/api/v1.php`, so a future `/api/v2` adds a parallel file/group without touching or duplicating v1). A minimal `GET /api/v1/health` endpoint establishes the routing and response conventions documented in `04_API_CONVENTIONS.md`: success responses wrapped in `{"data": ...}`, JSON error rendering for `api/*` requests (already configured in `bootstrap/app.php` since Phase 1), Laravel's standard 422 validation-error shape, and standard HTTP status codes — no proprietary API envelope was invented.
**Rationale:** Establishes the convention with real, tested code rather than documentation alone, per the Phase 3 mandate, while keeping the surface area minimal (one non-business endpoint) since no business modules are authorized yet.

### DEC-021 — Flutter foundation structure; routing and state management deliberately deferred
**Date:** 2026-09-10
**Status:** ACCEPTED
**Decision:** `apps/mobile/lib` is organized as `app/` (root widget/theme), `core/config/` (build-time configuration, e.g. API base URL via `--dart-define`), and `features/` (one folder per future feature area; `home/` exists today as a placeholder). No routing package (e.g. `go_router`) and no state-management framework (Provider/Riverpod/Bloc) are introduced — Flutter's built-in `Navigator`/`MaterialApp.home` is sufficient until a real feature (starting with Authentication) needs more.
**Rationale:** Matches "structure, not screens" — a maintainable foundation for future modules without speculative packages or layering that nothing yet needs. Both choices should be revisited when Phase 4 (Authentication) introduces the first real navigation/state requirements, not decided in the abstract now.

### DEC-022 — Authentication mechanisms: session/cookie for Admin, Sanctum bearer tokens for Mobile
**Date:** 2026-09-11
**Status:** ACCEPTED
**Decision:** The Admin Backoffice (Blade + Livewire) authenticates using Laravel's conventional session/secure-cookie authentication via the `web` guard — no bearer tokens for ordinary browser sessions. The Flutter mobile app authenticates using Laravel Sanctum personal access tokens, sent as `Authorization: Bearer <token>` — no cookie-based SPA/stateful authentication for Flutter, no OAuth server, no JWT infrastructure, no Passport. `laravel/sanctum` (^4.0) is installed; its `personal_access_tokens` migration is published as-is.
**Rationale:** Two client types, two conventional Laravel-native mechanisms, matching CLAUDE.md's Phase 4 instructions and the ~100-employee resource-efficiency direction (`02_ARCHITECTURE.md` §0) — avoids the operational overhead of an OAuth/JWT server for an internal tool this size. Sanctum's token model supports future multi-device use without inventing a refresh-token scheme.

### DEC-023 — No public self-registration
**Date:** 2026-09-11
**Status:** ACCEPTED
**Decision:** Company App has no `POST /register` route (web or API) and no public registration screen in either surface. All accounts are company-provisioned: for this phase, via `php artisan db:seed --class=Database\Seeders\AdminUserSeeder` (local/testing environments only) or Tinker; a future Staff Management phase may add an Admin-driven account-creation UI.

### DEC-024 — Transitional Admin Backoffice access flag, pending Phase 5 RBAC
**Date:** 2026-09-11
**Status:** SUPERSEDED by DEC-028
**Decision:** A boolean `users.is_admin` column (default `false`, not mass-assignable) is the sole gate on whether an authenticated account may enter the Admin Backoffice. It is checked once, at login time, in `App\Livewire\Auth\LoginForm`. This is deliberately minimal and will be superseded by Phase 5's granular role/permission system — `is_admin` is not intended to survive as a permanent authorization primitive.
**Rationale:** Phase 4 must distinguish "may enter the Admin Backoffice" from "is an authenticated user" (CLAUDE.md §9) without building any part of Phase 5's RBAC. A single boolean is the smallest mechanism that satisfies this without pre-building roles/permissions tables or policies.

### DEC-025 — Flutter authentication state management: plain `ChangeNotifier`
**Date:** 2026-09-11
**Status:** ACCEPTED
**Decision:** `AuthController` (in `lib/features/auth/state/`) extends Flutter's built-in `ChangeNotifier` and is consumed via `ListenableBuilder` — no third-party state-management package (Provider, Riverpod, Bloc, GetX) is introduced. `CompanyApp` owns a single `AuthController` instance for the app's lifetime and injects it into `AuthGate`.
**Rationale:** Phase 4 is the first phase with a genuine shared-state need (DEC-021 deferred this exact decision to here). One piece of app-wide state (authentication) doesn't justify a dependency-injection/state-management framework at this project's scale — `ChangeNotifier` is part of the Flutter SDK already in use and is sufficient. Revisit if a later phase's state needs (e.g., multiple independent feature stores, computed/derived state across many providers) outgrow it.

### DEC-026 — Flutter token persistence: `flutter_secure_storage`
**Date:** 2026-09-11
**Status:** ACCEPTED
**Decision:** The Sanctum bearer token is persisted on-device via the `flutter_secure_storage` package (iOS Keychain; Android EncryptedSharedPreferences/Keystore), behind a `TokenStorage` interface (`lib/features/auth/data/token_storage.dart`) so tests can substitute an in-memory fake. The token is never written to plain `SharedPreferences`, source code, or an unencrypted file.
**Rationale:** CLAUDE.md's Phase 4 instructions explicitly require platform secure storage for the auth token, not ordinary local storage. `flutter_secure_storage` is the standard, actively maintained Flutter package for this and is the only new package this phase adds for storage (paired with `http` for the API client itself).

### DEC-027 — Docker Compose is now the standard local backend development environment
**Date:** 2026-09-11
**Status:** ACCEPTED — supersedes DEC-013
**Decision:** A three-service Docker Compose stack (`nginx`, `app` = PHP-FPM, `mysql`) at the repository root is now the standard way to run the Laravel backend locally, replacing direct-install PHP/Composer/MySQL as the default. Flutter (`apps/mobile`) remains outside Docker entirely — it continues to run on the developer's machine, an emulator, or a physical device, connecting to the Dockerized (or directly-run) API via the existing `API_BASE_URL` build-time configuration (DEC-021). Direct installation of PHP/Composer, as documented before this phase, remains possible for a developer who prefers it — Docker is the new *standard*, not the only supported path. GitHub Actions CI is unchanged (still SQLite-based, per DEC-015) — Docker is a local development environment concern, not a CI concern.
**Rationale:** DEC-013's original reasoning (avoid idle container overhead and setup complexity at ~100-user scale) held while the backend had no real database engine decision to standardize around. Phase 3 (DEC-016) fixed MySQL as the production direction, and Phase 4 introduced Authentication — the first phase where "works on my machine" schema/engine drift (SQLite locally vs. MySQL in production) becomes a real correctness risk worth eliminating, not just a resource-efficiency tradeoff. A lean three-service stack (no Redis, queue worker, scheduler, WebSocket server, Mailpit, phpMyAdmin, or other always-on infrastructure beyond what's demonstrably needed) keeps this consistent with the resource-efficiency direction (`02_ARCHITECTURE.md` §0) while giving every contributor the same MySQL-backed environment the production system actually runs on.

### DEC-028 — Roles & Permissions: one role per user, centralized Gate override for Administrator
**Date:** 2026-09-11
**Status:** ACCEPTED — retires DEC-024
**Decision:** Company App's V1 authorization foundation is: a fixed `roles` catalog (`Administrator`, `Manager`, `Staff`), a distinct `permissions` catalog (dot-notation identifiers, e.g. `admin.access`, following DEC-004's naming convention), and a many-to-many `role_permissions` join. Each user has **at most one role** (`users.role_id`, nullable FK — not a many-to-many user↔role table); a user with no role has no permissions. Enforcement is centralized in a single `Gate::before` callback (`App\Providers\AppServiceProvider::boot()`): a user holding the Administrator role passes every ability check unconditionally (a deliberate, documented override — not explicit permission rows attached to Administrator, and not scattered `if ($user->is_admin)`/`if ($user->role === 'admin')` checks elsewhere); any other user's ability check resolves against their role's attached permissions, defaulting to deny. This makes Laravel's own `can` middleware, `Gate::allows()`, `@can`, and `$user->can()` inside future Policies all work against permission names with no per-permission `Gate::define` boilerplate. The Phase 4 transitional `users.is_admin` boolean (DEC-024) is retired: the column is dropped, and the Admin Backoffice's access chain becomes `auth` → `account.active` → `can:admin.access` → `/home`. No third-party RBAC package is introduced.
**Rationale:** At ~100 users, one role per user is the simplest schema that satisfies the product's actual authorization need (DEC-004's permission-oriented principle, applied without building unnecessary many-to-many user↔role infrastructure the phase's governing instructions explicitly warned against). A single centralized Administrator override is safer to maintain than requiring every future permission to be remembered and explicitly attached to Administrator (which risks accidentally locking out the highest-privilege role when a new permission is added), while still keeping the override in exactly one place rather than scattered through controllers/components. Manager and Staff intentionally start with no attached permissions — CLAUDE.md §10 explicitly allows this; their real permissions arrive with the modules that need them.

### DEC-029 — Organization Structure: flat Departments, single-department Teams/Positions, restrict-on-delete
**Date:** 2026-09-11
**Status:** ACCEPTED
**Decision:** Company App's V1 organization structure (Phase 6) is deliberately flat: `departments` (a major organizational unit, no sub-department hierarchy), `teams` and `positions` (each belonging to **at most one** department via a nullable `department_id` FK, never a many-to-many span across departments — resolving `02_ARCHITECTURE.md` §9's open question). All three share a two-state `App\Enums\OrganizationStatus` (`active`/`inactive`) lifecycle column, rather than soft-deletes — retiring a unit flips this instead of deleting the row, preserving any future references (e.g. Staff, Phase 7) without adding a second, overlapping lifecycle mechanism. A Department cannot be deleted while any Team or Position still references it (`409`, application-enforced, backed by a `restrictOnDelete()` foreign key); Teams/Positions themselves may be freely deleted in this phase (nothing yet depends on them). Team names and Position titles are unique *within their department scope* (or within the "no department" scope), not globally — a Position title in particular is expected to recur across departments (e.g. "Manager"). Two new permissions, `organization.view` and `organization.manage`, are added to the Phase 5 `RolePermissionSeeder`; `organization.view` is attached to Manager and Staff (viewing the company's structure is low-sensitivity company metadata), while `organization.manage` remains Administrator-only via the existing centralized `Gate::before` override (DEC-028) — no new authorization mechanism.
**Rationale:** At ~100 employees, a flat department list and single-department team/position membership is the simplest model that satisfies the actual requirement, avoiding a speculative hierarchy engine or many-to-many organizational graph the governing instructions explicitly warned against. Using one status enum instead of layering `SoftDeletes` on top avoids two competing "is this still around" answers for the same row. Restrict-on-delete (rather than cascade or silently nulling) protects relational integrity — a department can't vanish out from under structures still pointing at it. Scoping Team/Position uniqueness per department (rather than globally) reflects how real organizations actually name things, and department-scoping Manager/Staff's view-only access keeps this phase's permission catalog as small as Phase 5's, per CLAUDE.md §7's "define only the permissions genuinely required" instruction.

### DEC-030 — Staff: separate from User, self-referencing manager with bounded cycle guard, three-state employment lifecycle
**Date:** 2026-09-11
**Status:** ACCEPTED
**Decision:** Company App's V1 personnel record is `staff` — deliberately separate from `users` (the authentication/account model). `staff.user_id` is a nullable, **unique** FK to `users`: a Staff record may exist with no login access, a User may exist with no Staff record (e.g. the seeded local Administrator), and a User may link to at most one Staff record (DB-enforced, not just convention). No authentication data (credentials, tokens, account state) is duplicated onto `staff`. The Manager relationship is a self-referencing nullable `manager_id` on `staff`; a staff member cannot be their own manager, and assigning a manager is rejected if it would create a reporting cycle, checked by walking the proposed manager's own chain up to a small fixed bound (`Staff::wouldCreateCycleWith()`, 50 steps) rather than building general-purpose graph-cycle detection. Staff carries its own three-state employment lifecycle, `App\Enums\StaffStatus` (`active`/`inactive`/`separated`), mirroring `AccountStatus`'s established three-state V1 pattern rather than `OrganizationStatus`'s simpler two-state master-data lifecycle — "temporarily inactive" and "no longer employed" are meaningfully different for a person record, and this status is distinct from both `AccountStatus` (login/account state) and the future Phase 9 operational/current status (available, on leave, in the field, off duty). A Staff record's `department_id`/`team_id` must be mutually consistent — when both are supplied and the Team belongs to a Department, they must match; when `department_id` is omitted, it's derived from the Team. `employee_number` is admin-supplied and validated unique, not system-generated. Two new permissions, `staff.view` (Manager/Staff — the Staff Directory is company-wide) and `staff.manage` (Administrator-only, via the existing `Gate::before` override), extend the Phase 5/6 `RolePermissionSeeder` pattern. `DepartmentController`/`TeamController`/`PositionController::destroy` (Phase 6) are extended to also reject deletion when Staff still reference the record, and `StaffController::destroy` itself rejects deleting a staff member who still has direct reports — both `409`, backed by `restrictOnDelete()` foreign keys.
**Rationale:** Keeping `Staff` and `User` distinct (per the governing Phase 7 instructions) avoids a duplicate/parallel authentication concept and matches `03_DATABASE_MODEL.md`'s original anchor design ("staff is the organizational anchor," `users` is "a login"). A unique `user_id` is the simplest mechanism that prevents one login from silently representing two employees without inventing a many-to-many relationship nothing currently needs. Bounded manager-chain cycle detection is a few lines of maintainable code that satisfies "prevent obviously invalid reporting structures" without the complexity of a general graph algorithm — a real ~100-person org's chain depth is nowhere near the bound. A three-state employment lifecycle (rather than reusing `OrganizationStatus`'s two states) reflects that a person, unlike a department/team/position, has a real difference between "temporarily not active" and "separated," and keeping it distinct from `AccountStatus` avoids conflating "can this person log in" with "are they currently employed." Extending Phase 6's delete-protection into Staff (rather than leaving a gap) keeps the "prevent invalid organization structures" guarantee intact now that Staff can actually populate those relationships.

### DEC-031 — Clients & Contacts: required Client↔Contact ownership, two-state lifecycles, shared permissions, flat API resources
**Date:** 2026-09-11
**Status:** ACCEPTED
**Decision:** Company App's V1 customer-data foundation (Phase 8) is `clients` and `contacts`. A Contact always belongs to exactly one Client — `contacts.client_id` is **required**, `restrictOnDelete()`, never nullable — no client-less contacts and no many-to-many Contact↔Client relationship. `App\Enums\ClientStatus` (`active`/`inactive`) is Client's lifecycle, a two-state pattern mirroring `OrganizationStatus` (Department/Team/Position) rather than `StaffStatus`'s three states — a Client is business-relationship master data, not a person's employment record. `App\Enums\ContactStatus` (`active`/`inactive`) similarly gives a Contact a lightweight lifecycle so a person who has left their client organization can be preserved (not deleted) while excluded from "current contacts" views, without a richer employment-style state machine. `client_code` is **nullable**, unique when present, admin-supplied (no auto-numbering) — deliberately different from Staff's required `employee_number`, since a Client record is often created before any internal reference code is assigned. A Client's address is a small structured inline field set (`address_line1`/`address_line2`/`city`/`state_province`/`postal_code`/`country`), not a polymorphic/multi-address subsystem. At most one Contact per Client may have `is_primary = true`, enforced in `ContactController` inside a DB transaction (clear-then-set), not a DB partial-unique-index. Two new permissions, `clients.view` (Manager/Staff — the directory is company-wide) and `clients.manage` (Administrator-only via the existing `Gate::before` override), extend `RolePermissionSeeder`; Contacts share these same permissions rather than a separate `contacts.*` pair, since a Contact has no independent meaning apart from its Client. Both `/api/v1/clients` and `/api/v1/contacts` are flat top-level resources — Contact is filtered by `?client=<public_id>`, not nested under `/clients/{client}/contacts` — matching the Phase 6/7 precedent of a top-level filterable resource over deep nesting, even though `04_API_CONVENTIONS.md`'s original illustrative principle mentioned client-nested contacts as a hypothetical example before any real endpoint existed. A Client cannot be deleted while any Contact still references it (`409`, `restrictOnDelete()`-backed); a Contact may be freely deleted (nothing yet depends on it).
**Rationale:** Matches `03_DATABASE_MODEL.md`'s existing description of the Clients entity group ("`contacts` belong to a `client`... A `contact` is not a `user`") and the governing Phase 8 instructions' expected default relationship. Two-state lifecycles for both Client and Contact avoid a second, overlapping "is this still around" mechanism alongside `status` (no `SoftDeletes`), consistent with DEC-029's reasoning. A nullable, non-auto-numbered `client_code` reflects that unlike an employee (always assigned an HR number at hire), a client relationship commonly exists before any internal code is assigned. Sharing Client's permissions for Contact keeps the permission catalog as small as CLAUDE.md's Phase 8 instructions ask, since Contact is never independently meaningful apart from its Client. Flat, filterable top-level resources keep the API surface consistent with every real endpoint built so far (Departments/Teams/Positions, Staff), rather than introducing the first nested-resource route in the codebase for a case adequately served by filtering.

### DEC-032 — Staff Operational Status & Location Check-in: separate history tables, derived "current," scoped location visibility
**Date:** 2026-09-11
**Status:** ACCEPTED
**Decision:** Company App's V1 operational-visibility foundation (Phase 9) is two append-only history tables, deliberately separate from `staff.status` (Phase 7, employment lifecycle, DEC-030) and from any attendance/leave/payroll concept. `staff_statuses` (`App\Models\StaffOperationalStatus`) records `App\Enums\OperationalStatus` (`available`/`busy`/`in_meeting`/`in_field`/`off_duty`) changes — `staff_id`, `status`, `changed_by_user_id` (nullable — the acting user, self or an Administrator correction). `staff_checkins` (`App\Models\StaffCheckIn`) records explicit, user-triggered location check-ins (DEC-005 continues to govern — no continuous/background tracking) — `public_id` (ULID, DEC-017 — an Administrator addresses one directly for deletion), `staff_id`, required `latitude`/`longitude` (`decimal(10,7)`), optional `accuracy_meters`/`location_label` (free text, no Location Master module)/`note` (≤500 chars)/`status` (an `OperationalStatus` snapshot, informational only — it does not also write a `staff_statuses` row). Splitting `staff-status.view` (broad) from `location.view` (Manager-scoped) reflects that a status word ("busy") is materially less revealing than precise GPS coordinates — the governing instructions were explicit that ordinary Staff must never see company-wide precise location, and that Manager-to-direct-report visibility via the existing `manager_id` is preferable to inventing a new ACL engine. `cascadeOnDelete()` (rather than `restrictOnDelete()`) reflects that these are Staff-owned child records with no independent business meaning, unlike master data other tables reference. Modeling "update" as "append to the list `GET` already returns" is the smallest API surface that satisfies both "view current" and "view history" without a redundant second endpoint.

### DEC-033 — Projects & Project Membership: membership-based leadership, restrict-on-delete, scoped visibility
**Date:** 2026-09-11
**Status:** ACCEPTED
**Decision:** Company App's V1 work-management foundation (Phase 10) is `projects` and `project_memberships`. A Project optionally belongs to one Client (`client_id` nullable, `restrictOnDelete()`) — internal projects have `client_id = null`; no many-to-many Project↔Client relationship, and an inactive Client neither loses its existing Projects nor is blocked from receiving new ones (no status cascade). `App\Enums\ProjectStatus` (`planned`/`active`/`on_hold`/`completed`/`cancelled`) is a single lifecycle mechanism — no soft deletes or separate archival flag; `completed_date` is required when the effective status is `completed` (mirroring `StaffStatus::Separated`/`separation_date`, DEC-030), and reopening a completed project is permitted without clearing `completed_date`. Two new permissions extend `RolePermissionSeeder`: `projects.view` (Administrator via the centralized `Gate::before` override, and **Manager only** — not Staff, unlike every prior `*.view` permission) and `projects.manage` (Administrator-only, covering Project CRUD and all Project Membership writes — no project-lead self-management carve-out). Ordinary Staff visibility is instead scoped in-controller (`AuthorizesProjectVisibility`, the second real row-level authorization pattern after Phase 9's Manager→direct-reports scoping): a Staff member with a linked Staff record sees only Projects where they hold a Project Membership, applied to the primary `/api/v1/projects` endpoints themselves rather than a separate `/me/projects` route. `ClientController::destroy`/`StaffController::destroy` (Phases 8/7) are extended to also reject deletion while a Project/Project Membership references them, respectively; `ProjectController::destroy` itself rejects deletion while any Project Membership exists.
**Rationale:** A membership-based leadership model avoids the maintenance risk of two disagreeing "who leads this" answers once Project Membership already needs a role concept — the governing instructions explicitly favored this when a role-carrying Membership model already exists. Treating Project Membership as current-roster-only (not a history table) matches the governing instructions' "avoid duplicate-period complexity without a demonstrated requirement," since future Tasks/Work Logs are expected to reference `staff_id`/`project_id` directly and therefore don't lose historical data when a membership row is later removed — unlike Phase 9's `staff_statuses`/`staff_checkins`, which are genuinely historical by nature. `restrictOnDelete()` (not `cascadeOnDelete()`) on both Project Membership foreign keys reflects that Projects are master data future modules will anchor to, the same philosophy as Department/Client/Staff, not Phase 9's Staff-owned child data with no independent meaning. Scoping ordinary Staff to their own Project Memberships (rather than granting company-wide `projects.view`, as every previous `*.view` permission does) reflects that Projects may carry sensitive client-engagement information, unlike the company-wide Staff/Client/Organization directories — least privilege applied deliberately, per the governing instructions' explicit warning against blanket Staff visibility. Keeping `projects.manage` strictly Administrator-only (no project-lead carve-out) avoids the complicated role inheritance the governing instructions warned against; a future phase can reconsider this if the product owner wants project leads to self-manage membership.

### DEC-034 — Tasks: independent-capable, single-assignee, membership-scoped Project Lead authority
**Date:** 2026-09-11
**Status:** ACCEPTED
**Decision:** Company App's V1 foundational Tasks module (Phase 11) is `tasks`, built on top of Projects & Project Membership (Phase 10). Honoring DEC-006 (recorded at Phase 0), a Task **optionally** belongs to one Project — `tasks.project_id` is nullable, `restrictOnDelete()` — so internal company tasks never require an artificial Project. `App\Enums\TaskStatus` (`todo`/`in_progress`/`blocked`/`completed`/`cancelled`) and `App\Enums\TaskPriority` (`low`/`normal`/`high`/`urgent`, default `normal`) are both small, fixed enums with no restricted transition graph or workflow engine. A single nullable `assignee_staff_id` (`restrictOnDelete()`) is used — not a `task_assignees` many-to-many pivot — resolving `03_DATABASE_MODEL.md`'s open question for V1: no demonstrated requirement for multiple simultaneous assignees exists. `completed_at` is server-controlled only (both Form Requests reject a client-supplied value): set to `now()` whenever status transitions to `completed`, and **cleared** when a completed Task is reopened — a deliberate difference from Project's user-supplied, reopen-preserved `completed_date`, since a Task's completion timestamp is a derived workflow marker, not a historical fact an admin records. `created_by_user_id` (nullable, `nullOnDelete()`) is accountability metadata only, never an authorization primitive beyond Task creation itself.

New-assignment eligibility mirrors Project Membership's own pattern (Phase 10): only an `active` Staff member (Phase 7's `StaffStatus`) may be newly assigned, and — when the Task belongs to a Project — the assignee must currently be a member of that Project (enforced server-side in the Form Requests, never left to client-side filtering). Because `assignee_staff_id` references `staff` directly rather than through `project_memberships` — exactly what Phase 10's own handoff anticipated — **removing a Project Membership never touches an existing Task assignment**; assignment history is preserved even after the membership that originally made it eligible is gone, and an assignee's later `inactive`/`separated` employment status likewise never disturbs an existing assignment (only new assignments are checked).

Two new permissions extend `RolePermissionSeeder`: `tasks.view` (Administrator via `Gate::before`, and **Manager only**, mirroring `projects.view`'s reasoning) and `tasks.manage` (Administrator-only, unrestricted Task CRUD). No `tasks.assign`/`tasks.complete`/`tasks.delete`/etc. granular permissions were added. Instead, `App\Http\Controllers\Api\V1\Tasks\Concerns\AuthorizesTaskAccess` extends Phase 10's `AuthorizesProjectVisibility` row-level pattern to **writes**, not just reads — the first time this codebase scopes create/update authority outside route middleware: a Project Lead (`ProjectMembershipRole::ProjectLead` on the Task's own Project) may create/update Tasks scoped strictly to that Project — a bounded, Task-specific authorization decision that does not retroactively grant `projects.manage` or any other Project-management authority; a Task's assignee may update only its `status` field (self-service), enforced by diffing the validated payload's keys against the requester's authority tier rather than a new permission; an independent (project-less) Task's creation/management remains Administrator-only, since there is no Project Lead concept without a Project. Visibility mirrors this: `tasks.view` holders see every Task; otherwise a linked-Staff requester sees Tasks in Projects they belong to (any role) plus any Task assigned to them directly — never broader than the equivalent Project's own visibility.

`/api/v1/tasks` is a **flat, top-level resource** (filterable by `?project=`), not nested under `/projects/{project}/tasks` — unlike Project Membership, a Task is not inherently owned by a Project (DEC-006), so `04_API_CONVENTIONS.md`'s "prefer a top-level filterable resource... when a resource is more independent than owned" guidance applies, and this also sidesteps Phase 10's two-consecutive-Eloquent-parameter nested route-model-binding bug entirely. Task deletion is deliberately narrow: a hard `DELETE` is Administrator-only and permitted only while a Task is still `todo` (nothing has happened yet); anything with real activity is retired via ordinary `PATCH .../{public_id}` with `status: cancelled`, preserving history rather than destroying it. `ProjectController::destroy`/`StaffController::destroy` (Phases 10/7) are extended to also reject deletion while a Task references them, mirroring the existing Project Membership checks — Staff deletion is blocked regardless of the referencing Task's status, since assignment history survives even Project Membership removal.

Task comments/collaboration, present in `docs/ROADMAP.md`'s one-line Phase 11 description, were **not** implemented — the governing Phase 11 instructions for this session explicitly and repeatedly scoped them out alongside Work Logs/task activity/notifications, to be added by a future phase. `docs/ROADMAP.md` is updated to record this narrower, actually-implemented boundary, the same kind of scope note Phase 10 recorded for Project milestones.
**Rationale:** DEC-006 is a standing, accepted decision from Phase 0 — a Task model that silently required every Task to belong to a Project would directly contradict it, not merely leave a "nice to have" unbuilt. A single nullable assignee avoids the real complexity a `task_assignees` pivot would add (eligibility/removal semantics multiplied per row) without any V1 requirement demonstrating the need, consistent with the governing instructions' explicit warning against building it speculatively. Referencing `staff_id` directly rather than through Project Membership (rather than, say, blocking membership removal while Tasks are assigned) is the smallest safe rule available: it preserves business history unconditionally rather than forcing an administrator to choose between "block the removal" and "silently destroy the assignment," and it is exactly the design Phase 10 itself flagged as the anticipated shape for future Tasks/Work Logs. Extending row-level authorization to writes (not just Phase 9/10's reads) is the only way to give a Project Lead real, narrowly-scoped Task authority without either granting them the global `tasks.manage` permission (which the governing instructions explicitly warn against turning into broad authority) or inventing a bespoke `project-lead.manage`-style permission the catalog doesn't otherwise need. Making Task deletion conditional on `todo` status (rather than either "always allow" or "never allow") reflects that a `todo` Task represents no real work yet — nothing to lose — while anything further along is exactly the business history the phase's design goals call out preserving; `cancelled` already exists as the correct tool for retiring a Task with real activity, so no additional soft-delete column was warranted.

### DEC-035 — Work Logs: dual task/project anchor with a single source of truth, performer/creator distinction, Manager scoped to direct reports, Project Lead read-only
**Date:** 2026-09-12
**Status:** ACCEPTED
**Decision:** Company App's V1 Work Logs module (Phase 12) is `work_logs`, built on top of Staff/Projects/Project Membership/Tasks (Phases 7/10/11). A Work Log optionally references a `task_id` and/or a `project_id` — **never neither** (an un-anchored, generic activity log is out of scope) — resolving `03_DATABASE_MODEL.md`'s "optionally to a task and/or project" description for V1. When `task_id` is set, `project_id` is **always server-derived** from that Task's own `project_id` (itself possibly `null` for an independent Task, per DEC-006) and a client-supplied `project_id` alongside a `task_id` is rejected outright (application-enforced in `withValidator()` — this Laravel version has no declarative "prohibited if another field is present" rule) — this makes `Work Log.project = A` while `Work Log.task` belongs to Project B structurally impossible, not merely validated after the fact, while still persisting `project_id` as a real, indexed column (not purely derived at read time) since a Work Log may reference a Project directly with no specific Task. `staff_id` (the performer, required, `restrictOnDelete()`) is kept strictly distinct from `created_by_user_id` (nullable, `nullOnDelete()`, accountability-only, mirroring `tasks.created_by_user_id`, Phase 11) — entering a record is never conflated with having performed the work. Duration is modeled as `work_date` (required, not in the future) + `duration_minutes` (required positive integer, capped at 1440) — no start/end timestamps, no timer of any kind, and a single required `description` (≤2000 chars) rather than overlapping text fields.

Self-service creation eligibility (checked once, at creation, never re-validated) requires the performer's own Staff record to be `active`; for a Project-linked Task or a direct Project reference, the performer must be a **current Project member in any role** — not only a Task's assignee, since any active member may legitimately contribute to a Task without being its primary assignee; for an independent Task, the performer must be that Task's current assignee (the only linked-Staff visibility route Phase 11 grants for an independent Task). Historical preservation follows directly: a later Project Membership removal, Task reassignment, Staff status change, or Task status change never alters or removes an existing Work Log. Administrator-entered Work Logs (naming another Staff member via an explicit `staff_id`) deliberately **skip** this eligibility check — an Administrator is trusted to backfill/correct a record for someone who may since have left a Project or become inactive — but Task/Project existence and consistency are still enforced identically. No other role (Project Lead, Manager) may create or edit a Work Log on behalf of another Staff member.

Authorization introduces two permissions: `work-logs.view` (**Manager only**, scoped in-controller to the Manager's own direct reports via `Staff.manager_id` — mirroring `location.view`'s Phase 9 precedent, not `tasks.view`'s/`projects.view`'s company-wide Manager grant, since logged work duration/timing is treated as materially more sensitive than the Staff/Task/Project directories) and `work-logs.manage` (Administrator-only — create-for-others/edit-any/delete-any). A Project Lead gets **read-only** visibility (no permission — a row-level, in-controller check, `AuthorizesWorkLogVisibility`) into Work Logs referencing a Project they lead or one of its Tasks, and — deliberately unlike Phase 11's Task authority — **no** write authority of any kind; Work Logs get stricter rules than Tasks throughout, not an inherited copy of Task's Project Lead grant. An ordinary Staff member sees only their own Work Logs; Project membership never grants visibility into another member's logged work. Editing is limited to `work_date`/`duration_minutes`/`description`, by the performer (own record, any time, no arbitrary time window) or an Administrator (any record) — `staff_id`/`task_id`/`project_id` are immutable for everyone including Administrator after creation. Hard deletion is likewise limited to the performer (own record) or Administrator (any record) — no soft-delete column, since no downstream module in this phase (payroll/billing/reporting) yet references Work Logs, making a narrow self-correction capability low-risk.

The API is two genuinely separate endpoint families: `/api/v1/me/work-logs` (self-service list/create/edit/delete, performer identity always server-derived — reusing Phase 9's `RequiresLinkedStaff`; a `public_id` belonging to another Staff member returns `404`, not `403`, since its existence is itself sensitive) and `/api/v1/work-logs` (the supervisory/administrative surface — reads scoped in-controller with no `can:` middleware, writes gated by a conventional `can:work-logs.manage` route). `TaskController::destroy`/`ProjectController::destroy`/`StaffController::destroy` (Phases 11/10/7) are extended to also reject deletion (`409`) while a Work Log references them.
**Rationale:** A dual, single-source-of-truth anchor (Task and/or Project, never both inconsistently) satisfies the explicit governing requirement to support Project-linked Tasks, independent Tasks (DEC-006), and direct Project activity without persisting redundant, potentially-conflicting state — deriving `project_id` from `task_id` server-side is the smallest mechanism that makes the forbidden combination unrepresentable rather than merely rejected by a validation rule that could be bypassed by a future code path. Distinguishing performer from creator (rather than reusing Task's simpler always-self-or-null pattern) is required the moment any non-self creation path exists, per the governing instructions' explicit warning against conflating the two. Scoping Manager to direct reports (rather than company-wide, as Task/Project's `*.view` permissions do) reflects that logged work duration is a closer sensitivity match to Phase 9's location data than to a company directory — the governing instructions repeatedly warned against assuming Work Log sensitivity mirrors Task/Project sensitivity. Denying Project Lead any write authority (unlike Phase 11's scoped Task-management grant) reflects that Work Logs are historical records warranting stricter rules than Tasks, per the governing instructions' explicit direction not to inherit Task authority automatically. Checking eligibility only at self-service creation time (never retroactively) is the direct mechanism by which historical preservation is achieved without any special-case "don't touch old rows" logic — there is simply no code path that ever re-evaluates it. Allowing narrow, strictly self-or-Administrator-scoped hard deletion (rather than no deletion, or a soft-delete column) matches the governing instructions' caution about future reporting dependence while still providing a genuine self-correction mechanism appropriate for V1's current scale and the fact that no downstream module yet consumes Work Log data.

### DEC-036 — Leave Management: derived balances, single-stage Manager/Administrator approval, append-only history, no edit
**Date:** 2026-09-12
**Status:** ACCEPTED
**Decision:** Company App's V1 Leave Management module (Phase 13) is `leave_types` (configurable master data — `App\Enums\LeaveTypeStatus` `active`/`inactive`, an `is_paid` flag, no default annual allocation on the type itself), `leave_requests` (`App\Enums\LeaveRequestStatus` — `pending`/`approved`/`rejected`/`cancelled`, no `draft`), `leave_request_actions` (an append-only approval-history table — `App\Enums\LeaveRequestActionType` `submitted`/`approved`/`rejected`/`cancelled`), and `leave_balances` (per-staff/per-Leave-Type/per-calendar-year `allocated_days`, with `used_days`/`pending_days`/`remaining_days` **always derived live** from `leave_requests`, never a stored/cached column). `leave_requests` deliberately carries no `submitted_at`/`approved_at`/`rejected_at`/`cancelled_at` columns — submission is `created_at`, and every decision/cancellation timestamp lives only on `leave_request_actions`, avoiding a second source of truth for the same fact (extending DEC-032's "derive, don't cache" precedent from operational status/location to decision timestamps and balance usage alike).

Approval is single-stage: a Leave Request's **current** direct Manager (`Staff.manager_id`, evaluated at decision time, not submission time) or Administrator may approve/reject a `pending` request; a Manager can never approve their own request or an unrelated Staff member's, and a Staff member with no Manager can only be decided by Administrator — there is no fallback to a company-wide Manager grant and no multi-level approval chain. Approve/reject authority requires the actor to hold `leave-requests.view` **and** be the requester's current direct Manager (mirroring DEC-035's `work-logs.view`-plus-row-level-scope shape), enforced entirely in `LeaveRequestController`, not route middleware. Whichever Manager actually decided a request is permanently recorded on its `leave_request_actions` row — a later Manager reassignment never rewrites who actually made a past decision. There is **no edit endpoint** for a Leave Request at all (self-service or Administrator) — correcting a mistaken request means cancelling it and submitting a new one, the smallest coherent rule among the governing instructions' own alternatives.

Cancellation: the requester may cancel their own `pending` request at any time, or their own `approved` request only while `start_date` is still in the future; Administrator may cancel any `pending`/`approved` request at any time (correction authority, no time-window restriction); `rejected`/`cancelled` requests are immutable. No cancellation-approval workflow exists — cancellation is always a unilateral action by whichever of the two authorities is allowed to perform it at that moment.

Balance period is calendar year; a Leave Request may not span two different calendar years (a deliberate, documented V1 limitation avoiding split consumption across two balance rows). For a paid Leave Type, insufficient balance is rejected **at submission time only** (`allocated_days - already-approved - already-pending` for that Staff/Leave Type/year, excluding the request being created) — never re-checked at approval — inside a database transaction with `lockForUpdate()` on the relevant `leave_balances` row, preventing a concurrent-submission race; a Staff member with no `leave_balances` row yet is treated as `allocated_days = 0`. Unpaid Leave Types are never balance-checked (`allocated_days`/`remaining_days` report `null`, not `0`, in that case). Self-service *employment* eligibility (active Staff status) is checked only for self-service creation; an Administrator creating a request on a Staff member's behalf skips that one check (mirroring DEC-035's Work Log precedent). **Balance sufficiency is not an eligibility check exempted this way — it is enforced identically for both creation paths, with no Administrator override or negative-balance concept** (see this entry's Correction below), alongside Leave Type activity, date-range validity, and overlap, all of which are structural consistency rules applied identically regardless of who creates the request. Overlapping `pending`/`approved` requests for the same Staff member are rejected regardless of Leave Type; `rejected`/`cancelled` requests never block. `total_days` is a plain inclusive calendar-day count (no partial-day/half-day support, no business-day/holiday-aware calculation, weekends not excluded).

Four permissions extend `RolePermissionSeeder`: `leave-types.view` (Administrator/Manager/Staff, company-wide — a Staff member must browse active types to submit a request), `leave-types.manage` (Administrator-only), `leave-requests.view` (**Manager only**, scoped in-controller to direct reports — mirroring `work-logs.view`, not a company-wide grant), `leave-requests.manage` (Administrator-only — create on behalf of a Staff member, Administrator-cancel, set/update Leave Balance allocations). Self-service (`/me/leave-requests`, `/me/leave-balances`) needs no permission at all, mirroring Phase 9/12's domain-check pattern. `StaffController::destroy`/a new `LeaveTypeController::destroy` are extended/added with the established `restrictOnDelete()`-backed `409` pattern — a Staff member or Leave Type with any referencing Leave Request/Balance cannot be deleted, regardless of status.
**Rationale:** Deriving balance usage and decision timestamps rather than storing them mirrors this codebase's established, repeatedly-validated pattern (DEC-032's `Staff::latestOperationalStatus()`) for avoiding the classic dual-write bug class, and is the simplest model that is still correct for ~100 employees — no accrual engine, no ledger/adjustment infrastructure. A single-stage Manager-or-Administrator approval model, with authority resolved as a row-level in-controller check rather than a bespoke permission, follows DEC-034/DEC-035's precedent for scoping *write* authority without inventing a new permission-catalog entry per action. Checking the balance only at submission (never re-checking at approval) is the direct mechanism by which the `allocated_days` invariant holds without special-casing approval — every submission's check already accounts for every other outstanding request, and a rejected/cancelled request immediately frees capacity by being excluded from the derived sums. No edit endpoint (cancel-and-resubmit instead) is the smallest API surface among the governing instructions' candidate rules, and avoids ever having to decide what "editing a request already partway through approval" should mean. Skipping self-service *employment* eligibility (not balance/entitlement integrity) for Administrator creation mirrors DEC-035's Work Log precedent, applying the same "Administrator is trusted to backfill/correct" reasoning strictly to the domain-specific analogue of Work Log's own eligibility check (active Staff status) — not to balance sufficiency, which has no equivalent "trusted override" concept anywhere in this module.

**Correction (2026-09-12, post-review):** This entry's original text (and the matching passage in `docs/phases/V1_PHASE_13_DEFINITION.md`) incorrectly stated that Administrator-created requests skip *both* Staff active-status eligibility *and* balance sufficiency, and the initial implementation matched that incorrect text — `StoreLeaveRequestRequest`/`LeaveRequestController::store()` performed no balance check at all for Administrator creation. This was flagged in product-owner review: it created an implicit, undocumented Administrator negative-balance override, capable of driving `used_days + pending_days` above `allocated_days` (a negative derived `remaining_days`) — directly contradicting this same entry's "no override/negative-balance concept" decision. Fixed by extracting the balance-sufficiency check into two shared, single-implementation helpers — `App\Http\Requests\Leave\Concerns\ValidatesLeaveBalanceAvailability` (Form Request layer) and `App\Http\Controllers\Api\V1\Leave\Concerns\ChecksLeaveBalanceAvailability::assertSufficientBalance()` (the transactional, `lockForUpdate()`-guarded layer) — used identically by `StoreMyLeaveRequestRequest`/`MyLeaveRequestController` and `StoreLeaveRequestRequest`/`LeaveRequestController` alike, so there is exactly one balance rule, never two potentially-diverging copies. `ValidatesSelfServiceLeaveEligibility` was narrowed to cover only the Staff active-status check, which remains Administrator-bypassable. No override flag, allow-negative-balance configuration, new permission, new workflow, or balance-adjustment ledger was introduced — the fix only removed an unintended, implicit bypass. See the Phase 13 handoff's Deviations section for the corrected test coverage and quality-gate results.

### DEC-037 — Announcements: single-scope-type audience with union semantics, Administrator-only management, acknowledgement not read-tracking
**Date:** 2026-09-12
**Status:** ACCEPTED
**Decision:** Company App's V1 Announcements module (Phase 14) is `announcements` — a three-state lifecycle (`App\Enums\AnnouncementStatus`: `draft`/`published`/`archived`, one column as the single source of truth, no overlapping `inactive`/`expired` concept), created only as `draft`, moved to `published` and later `archived` exclusively via explicit action endpoints (`POST .../publish`, `POST .../archive`), never a generic status `PATCH`. `published_at`/`published_by_user_id` are both server-controlled, set only by the `publish` action, distinct from `created_by_user_id` (who drafted it) — the two may differ. No priority/importance field, no scheduled future `publish_at`, and no expiry: none were required by the governing roadmap line ("Company-wide/scoped announcements, recipients, acknowledgements") or any technical document, so none were built (CLAUDE.md §3). A `draft` may be freely edited or hard-deleted (nothing has been broadcast yet); a `published` announcement may still be edited (Option A among the governing instructions' candidates — a typo/audience fix is low-risk, unlike Leave Management's two-party approval record) but never hard-deleted, only archived; an `archived` announcement is fully immutable (no edit, no un-archive/republish) — correcting a mistake means creating a new announcement, mirroring Leave's "no edit; cancel and resubmit" precedent for a similarly terminal state. No parallel `announcement_actions` history table exists (contrast `leave_request_actions`): every transition has exactly one actor type (Administrator) and no decision content to preserve, so `status` plus `published_at`/`published_by_user_id`/`updated_at` already capture everything worth knowing — a second history table here would be exactly the workflow-engine CLAUDE.md's governing instructions warn against building without a demonstrated need.

Audience/targeting (`App\Enums\AnnouncementAudienceType`: `company_wide`/`scoped`) is a single scope type per announcement, never both at once: `company_wide` reaches every Staff-linked User; `scoped` targets one or more Departments and/or Teams via two plain many-to-many pivots (`announcement_departments`/`announcement_teams` — `announcement_id` `cascadeOnDelete()`, `department_id`/`team_id` `restrictOnDelete()`, no surrogate id/timestamps, mirroring `role_permissions`' "plain pivot" shape) with **union (OR), never intersection**, semantics — Department A + Team B means anyone in Department A **or** Team B. Visibility is evaluated against a Staff member's **current** `department_id`/`team_id` at read time, not a snapshot at publication — the simplest rule with no demonstrated need for snapshotting, and consistent with how every other org-structure-derived visibility check in this codebase already works. A Staff member with neither a Department nor a Team can only ever see `company_wide` announcements. Manager status and Project membership grant no extra Announcement visibility whatsoever — Announcements are an HR/organization-structure concern, mirroring Leave Management's identical exclusion of Project membership. The audience is always specified atomically: a write touching `audience_type`, `department_ids`, or `team_ids` must include `audience_type` itself (and, for `scoped`, a non-empty target set) — never an incremental patch to an existing target set, mirroring `ContactController`'s clear-then-set primary-contact transaction (DEC-031).

Acknowledgement (`announcement_acknowledgements` — `announcement_id` `cascadeOnDelete()`, `staff_id` `restrictOnDelete()`, unique per pair, `created_at` **is** the acknowledgement timestamp, no separate column) is explicitly **not** read-tracking: there is no unread/read concept, no reminder, and no mandatory-acknowledgement/compliance workflow — just a single, self-initiated, idempotent `POST .../acknowledge` (`firstOrCreate`, backed by the unique constraint), directly fulfilling the roadmap's own "recipients, acknowledgements" scope line without conflating it with "read," per the governing instructions' explicit warning. The management resource exposes a plain `acknowledgements_count` (via `withCount`, mirroring `ClientResource.contacts_count`, DEC-031) for at-a-glance accountability — never a per-staff acknowledgement list, percentage-read analytics, or reminder mechanism, which would cross into the "engagement/read-rate dashboard" the governing instructions warn against.

A single new permission, `announcements.manage` — Administrator-only, via the existing centralized `Gate::before` override (DEC-028) — gates the entire management surface (list, show, create, update, delete, publish, archive). Unlike every prior module, there is **no** companion `announcements.view` for Manager/Staff: ordinary employee visibility is served entirely by `/api/v1/me/announcements` (a domain check — a linked Staff record, mirroring Phase 9/12/13's `/me/...` self-service precedent, DEC-032/DEC-035/DEC-036), and a Manager holds no elevated Announcement authority of any kind in V1 — they read their own targeted feed exactly like any Staff member. `StaffController::destroy`/`DepartmentController::destroy`/`TeamController::destroy` (Phases 7/6, DEC-029/DEC-030) are extended to reject deletion (`409`) while any Announcement acknowledgement/audience row still references the Staff member/Department/Team, respectively.
**Rationale:** A single status column with explicit, one-way action endpoints for `publish`/`archive` is the smallest lifecycle that satisfies "hide unpublished/future content from ordinary employees" and "preserve broadcast history" without building a workflow engine or a second overlapping status/expiry concept, matching the governing instructions' explicit "avoid overlapping concepts" and "do not add a workflow engine" warnings. Making `published_at`/`published_by_user_id` strictly server-controlled and never re-set by an edit keeps "when/who actually published this" a durable historical fact independent of later content corrections. Choosing dedicated pivot tables over a polymorphic `announcement_audiences` table follows DEC-017's general preference for a dedicated shape when only two concrete target types exist and no third is in view, and mirroring `role_permissions`' surrogate-key-free pivot shape keeps the schema as lean as the data actually requires. Union (not intersection) semantics and current-membership (not snapshot) evaluation are both the simplest rules that satisfy the governing instructions without inventing combination logic or snapshot infrastructure nothing demonstrated a need for. Treating acknowledgement as a distinct, minimal concept — rather than either skipping it (the roadmap explicitly names it) or over-building it into read-tracking/compliance (which the governing instructions explicitly warn against) — is the direct resolution of what could otherwise read as a contradiction between the terse roadmap line and the detailed scope-exclusion list: build exactly the noun the roadmap names, nothing it doesn't. A single Administrator-only permission with no companion `*.view` reflects that, unlike Staff/Clients/Organization structure (company-wide directories every employee is equally entitled to see in full), an Announcement's *content* visibility is audience-scoped per employee by design — a blanket `announcements.view` would either over-grant (seeing every announcement regardless of audience) or be redundant with the self-service domain check already required for `/me/announcements`, so no new permission was warranted for it, consistent with CLAUDE.md §7's "define only the permissions genuinely required."

**Correction (2026-09-12, post-review):** This entry's original text (and the matching passage in `docs/phases/V1_PHASE_14_DEFINITION.md`'s Editing section) stated that a `published` Announcement "may still be edited" (Option A among the governing instructions' candidates), reasoning that a typo/audience fix is a low-risk operation. Product-owner review identified a real historical-integrity gap this created: an employee can acknowledge an Announcement's published content (version A), after which an Administrator could edit the same record's title/body/audience into version B while the original acknowledgement row remains unchanged — the system would then misrepresent what the employee actually acknowledged, directly contradicting this same entry's own preserve-don't-mutate rationale for published company communications (DEC-009/DEC-010).

**Fixed by making a `published` Announcement's content fully immutable**, not just its lifecycle-managed fields: `AnnouncementController::update()` now rejects (`409`) any `PUT`/`PATCH` unless the Announcement is still `draft` — the identical restriction `archived` already had, simply extended to cover `published` as well. `publish`→`archive` remains the only transition a `published` Announcement ever accepts. Correcting a mistake in already-published information is now exclusively a three-step workflow — archive the existing Announcement, create a corrected draft, publish the new one — never an edit. No revision/version history, content-version table, edit history, acknowledgement migration, acknowledgement invalidation, or acknowledgement-reset mechanism was introduced to support this: each new Announcement is simply a new, independent record, and an acknowledgement now permanently and provably corresponds to the exact configuration that existed at publication, since that configuration can never subsequently change. Tests asserting a `published` Announcement could be edited were replaced with tests asserting `409` for title, body, and audience changes independently, plus coverage that an acknowledged `published` Announcement cannot be edited and that an acknowledgement survives archival unchanged. No other decision in this entry changed.

### DEC-038 — Notifications: User-based recipient identity, typed (non-polymorphic) source reference, synchronous creation, single producer
**Date:** 2026-09-12
**Status:** ACCEPTED
**Decision:** Company App's V1 Notifications module (Phase 15) is a single table, `notifications` (`App\Models\Notification`) — a system-generated, in-app, user-facing alert about an event elsewhere in the application, not messaging, chat, a social feed, or arbitrary user-authored content. Recipient identity is the `User` account (`recipient_user_id`, `cascadeOnDelete()`), never `Staff` directly: a Notification can only ever be consumed through an authenticated login, and DEC-030 already established that Staff may exist without one — duplicating both `user_id` and `staff_id` was rejected as unneeded, since every current and anticipated producer already has a `User` in hand (a Staff-driven event resolves the Staff's linked User and skips Staff with none) and nothing in this phase's scope needs to display *historical* Staff identity independent of the User. This is also why, uniquely among every `/me/...` self-service surface in this API (Phase 9/12/13/14's precedent), `/api/v1/me/notifications` requires no linked Staff record at all — only `auth:sanctum` + `account.active` — since the resource's own identity is already User-scoped.

Schema is deliberately small: `public_id` (ULID, DEC-017), `type` (`App\Enums\NotificationType` — one case, `announcement_published`), `title` (≤200), `message` (≤500, short plain text), `source_type`/`source_public_id` (`App\Enums\NotificationSourceType` — one case, `announcement`), `read_at` (nullable). Source/context reference is Option A among the governing instructions' candidates — a typed pair of columns, not a generic polymorphic Eloquent relation (Option C) or a JSON metadata blob (Option B): only one concrete source type exists in this phase's actual scope, and this codebase has repeatedly chosen a dedicated shape over generic polymorphism when no second/third concrete type was in view (DEC-017's general preference, and DEC-037's own choice of two dedicated pivots over a polymorphic `announcement_audiences` table). There is no separate `action_type`/`action_public_id` — the `source` pair already tells a client exactly what to navigate to, and inventing a second, usually-identical field pair would be pure duplication for a V1 with a single producer. Read state is a single nullable `read_at`, set once and never reset — no read-history table, no per-device state, no delivery receipts.

Creation is synchronous, direct Eloquent creation inside the triggering request's own database transaction — no queue, no Laravel broadcasting/notification-channel package, no generic event-bus/listener framework. The roadmap lists "Phase 2 (queue infra)" as a Phase 15 dependency, but no queue worker was ever actually built (Phase 4A's Docker Compose stack explicitly excludes one) — inventing queue infrastructure solely to satisfy that roadmap line, for a company of ~100 employees where the largest single fan-out is at most ~100 rows, would be exactly the "infrastructure without a demonstrated need" this codebase has consistently avoided. Event integration is deliberately narrow: the roadmap names Phase 14 specifically as Phase 15's "first real notification producer," so exactly one producer was wired — `AnnouncementController::publish()`, via a new `NotifiesAnnouncementAudience` trait — resolving recipients with the same company-wide/scoped-Department/Team-union logic `ScopesAnnouncementVisibility` already uses for `/me/announcements`, but evaluated once, at publish time, as a **snapshot**: persisted Notification rows are never rewritten, added to, or removed because a Staff member's Department/Team changes afterward, deliberately unlike `/me/announcements`' own dynamic, current-membership feed — the two are now documented as intentionally different semantics for the same underlying audience concept. A Staff member with no linked User account is silently skipped (a Notification cannot be consumed by an account that doesn't exist). No separate idempotency key was introduced: `publish()` already only ever succeeds once per Announcement (its own `status !== draft` guard), so the fan-out structurally cannot double-fire; archiving never re-notifies. Leave Management and Tasks were evaluated and deliberately **not** wired — neither is named by the governing roadmap line or any technical document as a Phase 15 event source, so extending to them now would be exactly the "wire every prior module simply to make Notifications seem complete" the governing instructions warn against; this is recorded as a roadmap note, not built speculatively.

Notification content is deliberately generic and non-sensitive: the one wired producer sets `title` to the Announcement's own title (already broadcast, non-sensitive content, equally visible via `/me/announcements`) and a fixed, generic `message` ("A new company announcement has been published."), never the Announcement body — a client follows the notification's `source` to the Announcement's own, separately-authorized endpoint for full content, which enforces its own current authorization rules independently of the Notification row (a Notification may remain visible after its source becomes inaccessible; this is an accepted, documented gap, not a bypass, since no sensitive content ever lived in the Notification itself).

No new permission was introduced (`notifications.view`/`.manage` were considered and rejected) — authorization is plain per-row ownership (`recipient_user_id` must match the authenticated User), enforced entirely in `NotificationController`, with a foreign notification reported as `404` (not `403`), mirroring every other ownership-sensitive `/me/...` resource. There is no Admin management surface, no create/update/delete API, and no Flutter UI — Notifications are produced only by internal application code, and this phase ships infrastructure plus exactly one producer, not a communications platform.

**Discovered and fixed during this phase:** `App\Models\User` declared Laravel's default `Illuminate\Notifications\Notifiable` trait — a Phase 1 scaffold artifact, confirmed (by search) to be used nowhere in the codebase. Its own `notifications()`/`notify()` machinery expects a polymorphic `notifiable_type`/`notifiable_id`/`data` table shape fundamentally incompatible with this phase's own, differently-shaped `notifications` table; left in place, it would have been a latent landmine (a future accidental `$user->notify(...)` call would fail against the real schema). Removed, and replaced with a plain, explicit `User::notifications(): HasMany` relation against `App\Models\Notification` — this is a pre-existing scaffold/domain conflict discovered and corrected as part of this phase's own work (CLAUDE.md §2), not an unrelated refactor.
**Rationale:** A User-based recipient with no Staff duplication is the direct consequence of DEC-030's own optional Staff↔User linkage combined with "a Notification cannot be consumed by someone without an account" — Staff is a personnel/employment concept, User is an authentication concept, and a Notification inbox is inherently the latter. A typed source-reference pair over a polymorphic relation follows this codebase's established, repeatedly-validated preference (DEC-017, DEC-037) for the smallest concrete shape that fits actual scope, deferring genuine polymorphism to whenever a third source type is actually in view. Synchronous, transactional creation with no queue is the simplest architecture that is still correct at this company's real scale, and matches the governing instructions' explicit "avoid queues merely because Laravel Notifications often support them" guidance. Wiring exactly one producer — the one the roadmap itself names — rather than every plausible business event keeps this phase's blast radius to what was actually authorized (CLAUDE.md §3), leaving Leave/Task notification wiring as a deliberate, documented future decision rather than a scope-creep default. Publish-time snapshotting (rather than reusing `ScopesAnnouncementVisibility`'s dynamic query) is the only interpretation consistent with a Notification being "something that happened at a point in time" — a persisted historical record, not a live view — and is explicitly required by the governing instructions' Snapshot vs Dynamic Meaning section.

### DEC-039 — Messaging: Staff-identified participants, membership-only privacy, no real-time infrastructure
**Date:** 2026-09-12
**Status:** ACCEPTED
**Decision:** Company App's V1 Messaging module (Phase 16) is `conversations` (`public_id` ULID, `App\Enums\ConversationType` — `direct`/`group`/`project`, `name` nullable/group-only, `project_id` nullable/unique/`restrictOnDelete()`, `owner_staff_id` nullable/`restrictOnDelete()`/group-only), `messages` (`public_id` ULID, `conversation_id` `cascadeOnDelete()`, `sender_staff_id` `restrictOnDelete()`, `body` plain text ≤4,000 chars), and `conversation_members` (`conversation_id` `cascadeOnDelete()`, `staff_id` `restrictOnDelete()`, `last_read_message_id` nullable/`nullOnDelete()` against `messages`).

**Participant identity is Staff, not User** — a deliberate divergence from Notifications' DEC-038 choice. Messaging is person-to-person organizational communication, chosen from the Staff Directory (`staff.view`), not a raw User list; DEC-038's reasoning (a Notification can only ever be consumed through a login) doesn't generalize to a feature where the participants themselves are the point. Consequence: a User with no linked Staff record (e.g. the seeded local Administrator) cannot use Messaging at all — `AuthorizesConversationAccess::resolveAuthenticatedStaff()` returns `403` for such a User on every Messaging endpoint. A Staff member with no linked User may still be a conversation *member* (no add-time eligibility gate was introduced, mirroring the "checked only where it matters" precedent) — they simply can never themselves call the API, and the Notification fan-out below silently skips them, mirroring `NotifiesAnnouncementAudience`'s identical `whereNotNull('user_id')` skip.

**Direct conversations** are canonical per unique Staff pair — `ConversationController::storeDirect()` finds an existing `type = direct` conversation with both staff ids as members (via two `whereHas` clauses, correct because a direct conversation never has more or fewer than two members, by construction) before creating a new one; always exactly two participants, fixed for the conversation's lifetime (`ConversationMemberController` rejects any add/remove attempt on a direct conversation with `409`).

**Group conversations** are ad hoc and named; the creator becomes the group's single, permanent owner (`conversations.owner_staff_id`) — no co-owners, moderator roles, or ownership transfer exist in V1. Only the owner may add or remove another member; any member (owner included) may remove themselves. The owner invariant — the owner may never leave/be removed while any other member remains — is enforced as a single guard clause in `ConversationMemberController::destroy()` (`409` otherwise); once the owner is the conversation's sole remaining member, they may leave, leaving a harmless, terminal, memberless (but never-deleted) conversation row. This is the simplest rule that makes "an ownerless group with members still in it" structurally unreachable without inventing a transfer-of-ownership flow nothing in scope demonstrated a need for.

**Project conversations** are lazily created — no conversation row exists for a Project until `ProjectConversationController::storeOrShow()` is called for the first time by a current Project member (never eagerly for every Project, per the governing Phase 16 instructions), and membership is derived exclusively from Project Membership (Phase 10) at that moment; a plain unique index on `conversations.project_id` guarantees at most one per Project (a `QueryException` from a losing concurrent create simply falls back to fetching the winner's row — no distributed lock). `ProjectMembershipController::store()`/`destroy()` (Phase 10) are extended with a no-op-when-absent sync (`SyncsProjectConversationMembership`) so a Project's conversation membership — once it exists — never drifts from the real roster; there is no independently-managed project-conversation membership endpoint (`ConversationMemberController` rejects both add and remove on a `project`-type conversation with `409`).

**Messages are immutable after sending** — no edit, no soft-delete/tombstone, no hard-delete endpoint of any kind exists anywhere in this API; message history is retained indefinitely (no retention/cleanup job). `body` is capped at 4,000 characters — a deliberate bound between a single line and Announcement's 10,000-character broadcast body, appropriate for a chat message; no rich text, no HTML sanitization subsystem, mirroring Announcement's plain-text precedent (DEC-037).

**Read state is the minimum non-redundant representation**: `conversation_members.last_read_message_id` alone (no separate timestamp) — message ordering is already exact via the `messages` table's own auto-increment `id`, so a parallel timestamp would duplicate the same fact. Unread count is always derived (`ConversationMember::unreadCount()`, a live `COUNT` query), never a stored/cached column, extending this codebase's established "derive, don't cache" precedent (DEC-032/DEC-036) to Messaging. Sending a message updates the sender's own `last_read_message_id` to that message in the same transaction (they have obviously read their own message); `POST /conversations/{public_id}/read` marks the caller's own membership read up to the conversation's latest message at call time — idempotent, no per-message read receipts, no "seen by" list.

**Notification integration (the roadmap's own "notification of new messages" dependency on Phase 15):** `NotifiesConversationMembers`, a second real producer mirroring `NotifiesAnnouncementAudience`'s exact synchronous, transactional, no-queue shape, extends the closed `NotificationType` (`MessageReceived`) and `NotificationSourceType` (`Conversation`) enums by exactly one case each. Every sent message fans out one Notification per other current member with a linked User account — the sender is always excluded, and (per the governing instructions) multiple messages are never collapsed/deduplicated into one notification, unlike Announcement's inherently single-fire `publish()` guard. Content is deliberately generic and **identical regardless of conversation type** — a fixed title/message, never the message body, the sender's name, or the conversation/group/project name — simpler and more conservatively safe than branching per type, and consistent with Announcement's "never leak source content into the notification" precedent. The Notification's `source` points at the conversation (`{type: "conversation", public_id}`), never at the message itself — there is no individual message endpoint to navigate to.

**Authorization is membership-only — no `messages.view`/`messages.manage` permission was introduced**, and none is planned. `AuthorizesConversationAccess` never calls `$user->can(...)`, so Administrator's centralized `Gate::before` override (DEC-028) is never invoked for Messaging at all — this is the second place in the codebase (after Notifications' ownership check, DEC-038) where Administrator's usual "sees everything" behavior is deliberately absent by construction, not by a special-cased carve-out. A conversation/message the requester isn't currently a member of is `404`, never `403` — existence is itself sensitive, mirroring every other ownership-scoped resource in this API. `05_SECURITY_MODEL.md`'s pre-existing Messaging Privacy section ("no general admin-can-read-all default") is now implemented, not merely aspirational. `StaffController::destroy()`/`ProjectController::destroy()` are extended with the established `409`-then-`restrictOnDelete()` pattern for conversation membership, conversation ownership, message authorship, and Project conversation existence, respectively — the same relational-integrity philosophy as every prior module.

**No real-time/WebSocket infrastructure was introduced** — Phase 16 is request/response API only, resolving `02_ARCHITECTURE.md` §5/§9's long-open "real-time transport" question in favor of deferral: no Laravel Reverb, WebSockets, Redis, queue workers, broadcasting, or managed real-time vendor (Pusher/Ably). A future client is expected to poll (e.g. `GET .../messages`, unread counts) rather than receive push updates. `02_ARCHITECTURE.md` §1's architecture diagram — which depicted "Redis (cache/queue/broadcast) + Queue workers" as though already built — is corrected to reflect what Phase 4A (DEC-027) actually shipped (no such service exists anywhere in this application) and to record this deliberate deferral, not a stale aspiration.

**Not introduced:** attachments/files, message/conversation search, archive/mute, reactions, mentions, typing indicators, online/presence state, rich text/HTML, Team- or Department-linked conversations, visible per-message read receipts, an Admin moderation/read-all capability of any kind, external push/email/SMS delivery, retention/cleanup jobs, a generic polymorphic event bus, or Messaging-specific audit logging (Audit Logging, DEC-009, remains an unbuilt, project-wide, pre-existing gap — not something this phase silently invented a one-off version of); no Flutter mobile screens (a deliberate product-owner decision for this phase, diverging from `06_UI_UX_GUIDELINES.md`'s "Messages" primary-nav placement, which remains aspirational until a future phase builds it).
**Rationale:** Every structural choice here either extends an already-validated codebase precedent (derive-don't-cache for read state, typed non-polymorphic Notification sources, membership/ownership-only row-level authorization with no bare permission, `restrictOnDelete()` for anchor data vs. `cascadeOnDelete()` for pure child rows, lazy/no-eager-creation matching DEC-006/DEC-033's "don't build what nothing demonstrated a need for") or resolves a question `02_ARCHITECTURE.md` explicitly deferred "no earlier than the Messaging/Notifications phases" (real-time transport) in the direction the resource-efficiency direction (§0) and every prior phase's actual behavior already pointed. Staff-based (not User-based) participant identity is the one deliberate departure from the most recent precedent (DEC-038), justified by Messaging being fundamentally a Staff-to-Staff feature rather than an account-scoped inbox. The owner invariant and project-conversation lazy-creation-with-sync are both the smallest mechanisms that make an invalid state unreachable by construction, rather than merely validated after the fact — consistent with this codebase's established preference throughout Phases 10–15.

### DEC-040 — Scheduler: hybrid read-time aggregation + Schedule Entries, Milestones built to correct a false Phase 10 dependency
**Date:** 2026-09-12
**Status:** ACCEPTED
**Decision:** Company App's V1 Scheduler (Phase 17), preceded by a product-owner-reviewed planning audit (mirroring Phase 16's DEC-039 precedent) that resolved the roadmap's terse "unified schedule/calendar" line into concrete architecture, is a **hybrid**: (1) a unified, read-time API projection (`GET /api/v1/schedule`) that aggregates exactly four sources — manually created Schedule Entries, Task due dates, approved Leave Requests, and Project Milestones — and (2) a lightweight, Scheduler-owned entity, `schedule_entries`, for activities with no other system-of-record module. **No calendar rows are ever copied or cached into a generic table for the three aggregated sources** — Tasks, Leave Requests, and Project Milestones remain their own systems of record, joined into the unified representation only at read time (`App\Http\Controllers\Api\V1\Scheduling\ScheduleController`), extending this codebase's established "derive, don't cache" precedent (DEC-032/DEC-036/DEC-039) to cross-module aggregation for the first time. The unified projection uses a closed, non-polymorphic discriminator, `App\Enums\ScheduleSourceType` (`schedule_entry`/`task`/`leave`/`project_milestone`), mirroring `NotificationSourceType`'s typed-reference shape (DEC-017/DEC-038) — deliberately distinct from `App\Enums\ScheduleEntryActivityType` (a Schedule Entry's own `meeting`/`client_visit`/`service_appointment`/`company_event`/`training`/`internal_activity`/`other` kind), never conflated with each other.

**Schedule Entries** (`schedule_entries` — `public_id` ULID, `creator_staff_id` required/`restrictOnDelete()`, `title`, `description` nullable ≤5,000 chars, `activity_type`, `starts_at`/`ends_at` UTC `datetime`, `is_all_day` boolean, `project_id` nullable/`restrictOnDelete()`; `schedule_entry_participants` — a plain composite-PK pivot, `staff_id` `restrictOnDelete()`, mirroring `role_permissions`' surrogate-key-free shape) are the minimal V1 model for "an activity with no other module" — never split into dedicated Meeting/Visit/Appointment/Training/Company Event tables, all of which are simply `ScheduleEntryActivityType` values on one generic entity. The creator is a real, standing business-authority column (unlike `tasks.created_by_user_id`'s accountability-only pattern) since they retain edit/delete authority over their own entry for its lifetime — `restrictOnDelete()`, not `nullOnDelete()`. Participation (`schedule_entry_participants`) carries **no** RSVP/invited/accepted/declined/tentative state — it means only "this appears on that Staff member's schedule and they may view it"; the creator is deliberately never duplicated into this pivot (avoiding unneeded duplicated state), since creator visibility is already derived from `creator_staff_id`.

**Date/time design:** this is the first module in the codebase with genuine time-of-day scheduling. A **single pair** of UTC `datetime` columns (`starts_at`/`ends_at`) is used for both timed and all-day entries — the cleanest, minimally redundant representation, resolved against the alternative of a second, date-only column pair (which would create exactly the kind of "which pair is authoritative" ambiguity this codebase's other dual-representation decisions have consistently avoided, e.g. Work Log's single derived-`project_id`). For a timed entry, the columns hold the real start/end instants; for an all-day entry, they hold the start-of-day/end-of-day instants of the entry's date range in a single, explicitly configured company timezone (`config('scheduling.company_timezone')`, `App\Support\CompanyTimezone`, env `SCHEDULING_COMPANY_TIMEZONE`, default UTC) converted to UTC — a genuine, meaningful boundary, never an arbitrary invented time. `App\Support\Scheduling\ScheduleEntryTiming` is the single shared implementation reused by both the Form Requests (coherence validation — a malformed date/datetime or an end before the start is rejected with a 422) and the controller (final persisted values), so there is exactly one timing rule, never two potentially-diverging copies (mirroring `ChecksLeaveBalanceAvailability`'s DEC-036 Correction precedent). No per-User/per-Staff timezone field was added — V1 assumes a single company-wide timezone, consistent with `01_PRODUCT_REQUIREMENTS.md` §6's existing "multi-language/localization out of scope" assumption and this codebase's resource-efficiency direction; nothing hardcodes a timezone string outside this one config value and its single accessor class. The three date-only aggregated sources (Task due dates, Leave start/end dates, Milestone due dates) are projected into the unified representation using this exact same day-boundary rule — never given a fabricated time-of-day, and never mutating their own source records.

**Project Milestones** (`project_milestones` — `public_id` ULID, `project_id` **required**/`restrictOnDelete()`, `title`, `due_date`, `status`) are the minimal target-date marker concept the Phase 17 roadmap dependency ("Depends on: ... Phase 10 (Milestones)") incorrectly assumed Phase 10 had already built — Phase 10 explicitly deferred it (see `docs/phases/V1_PHASE_10_DEFINITION.md`'s own exclusions and `03_DATABASE_MODEL.md` §1's "not yet implemented" note). `App\Enums\ProjectMilestoneStatus` (`pending`/`completed`/`cancelled`) is deliberately smaller than `TaskStatus` — a milestone is a point-in-time target, not ongoing work with its own progress states, so no `in_progress`/`blocked` equivalent exists; no percent-complete, dependency graph, nested milestones, recurrence, or workflow engine was built. Milestones are nested under their Project (`/api/v1/projects/{project}/milestones`, mirroring Project Membership's genuine nesting, Phase 10) rather than a flat top-level resource like Tasks — a Milestone, unlike a Task, has no independent existence apart from its Project (DEC-006 has no Milestone analogue).

**Authorization — no new permission was introduced anywhere in this phase**, per the governing Phase 17 instructions' explicit direction to prefer established row-level patterns over a blanket `schedule.view`/`schedule.manage` permission that would expose private entries. Schedule Entry visibility/authority (`App\Http\Controllers\Api\V1\Scheduling\Concerns\AuthorizesScheduleEntryAccess`) is resolved entirely in-controller, mirroring Tasks' `AuthorizesTaskAccess` (DEC-034) exactly in shape: Administrator (a direct `hasRole()` check, mirroring `AuthorizesWorkLogVisibility`/`AuthorizesLeaveRequestVisibility`) sees and manages everything; otherwise a Staff-linked requester may view an entry they created, one they participate in, or one linked to a Project their *existing* Project visibility legitimately allows them to see (`AuthorizesProjectVisibility`'s exact rule — `projects.view` or current membership — reused, never re-invented); manage authority (update/delete) is the creator, a Project Lead of the entry's linked Project, or Administrator, with a mere participant strictly read-only. **A Manager gains no automatic visibility into a direct report's private (non-Project-linked) Schedule Entry merely from the manager relationship** — a deliberate, explicit product-owner decision distinguishing Schedule Entries from Work Logs/Leave Requests (where `work-logs.view`/`leave-requests.view` do grant Manager-of-direct-reports visibility): a personal calendar entry is treated as more private than logged work or a leave request. Project Milestone authorization (`AuthorizesMilestoneAccess`) reuses `AuthorizesProjectVisibility` as-is for reads and the existing `projects.manage` permission (already unconditionally granted to Administrator via the centralized `Gate::before` override, DEC-028 — requiring no new permission) plus a Project Lead check (mirroring `AuthorizesTaskAccess`'s identical carve-out) for writes. Every unauthorized-access case follows this codebase's established 404-vs-403 convention: an entry/milestone outside the requester's visibility is `404` (existence is sensitive); one they can see but may not modify is `403`.

**Task/Leave/Milestone aggregation preserves each source's own existing visibility rule exactly** — Task via a private, non-aborting replica of `AuthorizesTaskAccess`'s rule (kept self-contained in `ScheduleController` rather than modifying Tasks' own established, tested trait, minimizing this phase's blast radius); Leave via a replica of `AuthorizesLeaveRequestVisibility`'s Administrator/Manager-of-direct-reports rule, **plus one deliberate addition specific to this personal-schedule context**: a Staff member always sees their own approved Leave here, exactly as they already can via `/api/v1/me/leave-requests` — not a new visibility grant, just this endpoint reusing existing self-service access instead of requiring a second round-trip; Milestone via `AuthorizesProjectVisibility`'s exact rule. **Only `approved` Leave Requests ever appear** — `pending`/`rejected`/`cancelled` are always excluded, resolving the roadmap's own "leave" aggregation line narrowly and safely (a pending request is not yet a real calendar commitment, and rejected/cancelled ones never were). Leave contributes nothing when a `project` filter is applied (Leave has no Project association) rather than silently matching zero rows "by luck" of an always-false comparison.

**API:** `GET /api/v1/schedule` — `from`/`to` **required** (`to` must not precede `from`), optional `source`/`activity_type`/`project` filters, following `04_API_CONVENTIONS.md`'s "flat, filterable top-level resource" convention rather than separate month/week/day view endpoints (a calendar "view" is a client rendering concern). It returns Laravel's standard `LengthAwarePaginator` response shape (`data`/`links`/`meta`, identical to every other collection endpoint) — but is fed by an **in-memory merge** of each source's own small, independently authorized, date-range-scoped query rather than one SQL query, since a genuine multi-source aggregation across four differently-shaped, differently-secured tables cannot be expressed as a single portable SQL query without a fragile, per-source-duplicated UNION; at this company's scale (~100 employees), the total rows within a realistic date range is small enough that fetching each source's matching rows and paginating the merged, sorted result in PHP is simple, correct, and not a performance concern. This is a documented deviation in *how* the paginator is fed, not a new pagination *convention* — the response contract is unchanged. `GET/POST /api/v1/schedule-entries` plus `GET/PUT/PATCH/DELETE .../{public_id}` — a flat, top-level resource (mirroring Tasks, not nested); `GET/POST /api/v1/projects/{project}/milestones` plus `GET/PUT/PATCH/DELETE .../{milestone}` — genuinely nested (mirroring Project Membership), with `withoutScopedBindings()` on the two-consecutive-Eloquent-parameter routes (Phase 10/16's established fix) and an explicit in-controller ownership check (`milestone.project_id === project.id`) in place of Laravel's guessed scoping. No response anywhere exposes an internal numeric id.

**Explicitly not introduced, per the governing Phase 17 instructions:** recurring events/recurrence rules/generated occurrences/exception dates; RSVP/attendance-response workflow; reminders of any kind or Notification integration for Schedule Entries (no Scheduler Notification producer was wired — a deliberate divergence from Messaging/Announcements' precedent, since true time-based reminders would require cron/a Laravel Scheduler worker/queues, none of which exist in this application, DEC-039/§6 of `02_ARCHITECTURE.md`, and an at-creation notification was judged unnecessary complexity for this phase); conflict/overlap detection (overlapping Schedule Entries are valid data — Leave's own overlap rule, DEC-036, is Leave-specific and was never generalized here); Department/Team-linked Schedule Entries (Project-linked only); attachments/files; Google Calendar/Outlook/`.ics` integration of any kind; Flutter mobile Scheduler UI or Admin Backoffice Scheduler UI; Scheduler-specific audit logging (Audit Logging, DEC-009, remains an unbuilt, pre-existing, project-wide gap); WebSockets/Reverb/Redis/queues/broadcasting/rich text; per-user/per-Staff timezone fields.

`docs/ROADMAP.md`'s Phase 17 entry is corrected: "Depends on: Phase 13 (Leave), Phase 11 (Task deadlines), Phase 10 (Projects — Milestones deferred there, implemented here)" — the dependency line no longer misrepresents Phase 10 as having built Milestones.
**Rationale:** Aggregating at read time rather than copying data into a generic `calendar_events` table (the very question `03_DATABASE_MODEL.md` §1 left explicitly open for this phase) is the direct, required consequence of this codebase's repeatedly-validated "derive, don't cache" principle — a copied/synced calendar row would immediately create the classic dual-write bug class (a Task's due date changing without its calendar copy following) that DEC-032/DEC-036 were each written specifically to avoid, and duplicating Leave's already-sensitive, already-carefully-scoped visibility rule into a second, independently-secured table would be a direct, unforced privacy regression. A single pair of UTC datetime columns for Schedule Entries (rather than a redundant date/datetime pair keyed off `is_all_day`) is the smallest schema that is still unambiguous — exactly the kind of dual-representation trap this codebase's other design decisions (Work Log's single derived `project_id`, Leave's derived balances) have consistently engineered away. Reusing `AuthorizesProjectVisibility`/`AuthorizesTaskAccess`'s exact existing rules — rather than inventing new Scheduler-specific visibility logic, or worse, a blanket permission — keeps Phase 17's authorization surface as small as CLAUDE.md §7 asks and guarantees the Scheduler can never show a Staff member data their source module would already deny them. Denying Managers automatic visibility into a direct report's private Schedule Entries (unlike Work Logs/Leave) reflects a real, product-owner-articulated distinction: a personal calendar entry ("dentist appointment," "1:1 with a report") is treated as more private than logged work hours or a leave reason, and the governing instructions were explicit that this must not be assumed to inherit Work Log/Leave's Manager-scoping by default. Building Milestones now, deliberately small, is the direct, honest resolution of a real, previously-undetected gap between the roadmap's stated dependency and what Phase 10 actually shipped — rather than either silently ignoring the roadmap's own words or inflating this phase's scope with a full project-planning subsystem nothing has demonstrated a need for.

### DEC-041 — Service Reports: required Client anchor, four-state review workflow, no new permission, and the shared attachment infrastructure
**Date:** 2026-09-13
**Status:** ACCEPTED
**Decision:** Company App's V1 Service Reports (Phase 18), preceded by a product-owner-reviewed planning audit (mirroring Phase 16/17's DEC-039/DEC-040 precedent) that resolved the roadmap's terse "Service report creation, review, attachments" line into concrete architecture, is: a `service_reports` record with a **required** `client_id` (the business anchor — never a generic internal activity record), **optional** `project_id`/`task_id` (mirroring DEC-006's optional-Project precedent), and a required `creator_staff_id` (the primary performer, a real standing business-authority column mirroring `schedule_entries.creator_staff_id`, not mere accountability metadata). Relational coherence between Client/Project/Task is enforced at the application layer (`App\Http\Requests\ServiceReports\Concerns\ResolvesServiceReportReferences`): a supplied Project must belong to the selected Client; a supplied Task must not contradict the selected Client/Project, with `project_id` server-derived from `task_id` when omitted (extending Work Log's identical single-source-of-truth rule, DEC-035, with an added Client-coherence layer Work Log never needed). `creator_staff_id` is immutable at every status. Client/Project/Task are immutable together with the rest of the report's content once it leaves `draft` (`submitted`/`reviewed`/`rejected`) — see this entry's Correction below for how that differs from Work Log's precedent.

**Correction (2026-09-13, post-review):** This entry's original text (and the matching passages in `docs/phases/V1_PHASE_18_DEFINITION.md`, `02_ARCHITECTURE.md` §28, and `CHANGELOG.md`) stated that the entire Client/Project/Task/creator anchor was "immutable after creation," directly mirroring Work Log's `staff_id`/`task_id`/`project_id` immutability (DEC-035) — and the initial implementation matched that text: `UpdateServiceReportRequest` accepted no `client_id`/`project_id`/`task_id` fields at all. Product-owner review identified this as stricter than the approved Phase 18 behavior: a draft Service Report's Client/Project/Task must remain correctable up until submission, exactly like every other draft field, not fixed the instant a draft is created. Work Log's precedent does not generalize here because a Work Log has no draft/submitted lifecycle to correct a mistake within — deleting and recreating is Work Log's only option, whereas a Service Report's own `draft` state already exists precisely to allow correction before commitment. Fixed by accepting `client_id`/`project_id`/`task_id` in `UpdateServiceReportRequest` (still never `creator_staff_id`, which remains immutable at every status, including `draft`) and adding `App\Http\Requests\ServiceReports\Concerns\ResolvesServiceReportReferences::validateClientProjectTaskCoherenceForUpdate()` — the update-time counterpart to the creation-time coherence check, applied to the *effective* combination (a changed field's new value, or the existing report's current value for any field left untouched, with the single-source-of-truth project-from-task derivation re-applied whenever the task changes and no explicit project accompanies it) so a Client change can never silently leave an incompatible Project/Task in place, nor can any request persist a temporarily inconsistent combination. `ServiceReportController::update()` resolves the same public IDs to internal ones and re-derives `project_id` identically to `store()`. The immutability boundary itself is unchanged in spirit — once a report leaves `draft`, its anchor is exactly as immutable as every other field, enforced by the same existing `isEditable()`/`409` check — only the *within-draft* editability was too strict. No workflow, attachment, or privacy behavior changed. See the Phase 18 handoff's Deviations section for the corrected test coverage and quality-gate results.

**Workflow — exactly four states, no new permission.** `App\Enums\ServiceReportStatus` (`draft`/`submitted`/`reviewed`/`rejected`) is a deliberately smaller machine than a generic draft/submitted/approved/completed chain: `reviewed` is the single final successful state (a Service Report documents work already performed, unlike a Task, which continues after approval — there is no separate "approved" vs "completed" distinction). Normal flow: `draft` → `submitted` → `reviewed`, or `submitted` → `rejected` → (`return-to-draft`) → `draft` → `submitted` (recorded as `resubmitted`, distinct from the original `submitted`, in `service_report_actions` — an append-only history table mirroring `leave_request_actions`' exact shape, DEC-010). Every transition is an explicit action endpoint (`submit`/`review`/`reject`/`return-to-draft`), never a generic status PATCH — the same discipline Announcements (DEC-037) and Leave (DEC-036) established. `draft` is freely editable (content, participants, attachments) by its creator or Administrator; `submitted`/`reviewed`/`rejected` are content- and attachment-immutable, with `rejected` requiring `return-to-draft` before any further edit — mirroring Announcement's "immutable once published" content-integrity precedent, extended here to a workflow with a correction path Announcements never needed.

**Visibility — deliberately narrower than Schedule Entries' model (DEC-040), no new permission.** A Service Report is visible to its creator, its listed Staff participants, the creator's *current* direct Manager (`Staff.manager_id`, evaluated live — a plain relationship check, not a `*.view` permission grant, mirroring `AuthorizesLeaveRequestVisibility`'s `isDirectManagerOf()` shape), and the linked Project's Project Lead (reusing the established `ProjectMembership` check, mirroring `AuthorizesTaskAccess`/`AuthorizesScheduleEntryAccess`), plus Administrator (a direct role check, unconditional). Per the governing Phase 18 instructions' **explicit rejection of a broad `service-reports.view` permission that would grant every Manager company-wide visibility**, this codebase's now-familiar "Manager holding `projects.view` sees every Project-linked item" shape (Schedule Entries, DEC-040) is deliberately **not** replicated here — only an actual Project Lead relationship, or the actual manager-of-record relationship, grants visibility; holding a Manager role by itself grants nothing. Review authority (the creator's current Manager, the linked Project's Project Lead, or Administrator — never the creator themselves, defensively guarded exactly like `LeaveRequestController::authorizeDecisionAuthority()`) and draft-management authority (edit/delete/attachment mutation/submit/return-to-draft — creator or Administrator only) are both resolved entirely in-controller (`App\Http\Controllers\Api\V1\ServiceReports\Concerns\AuthorizesServiceReportAccess`) — participants gain visibility but never workflow-management authority.

**Creation authority mirrors Work Log's Administrator-on-behalf precedent (DEC-035) exactly.** Any active User with a linked, active Staff record may create their own Service Report; a Project-linked report requires current Project membership (any role), an independent-Task-linked report requires being that Task's current assignee — both checked only at creation, mirroring Work Log's self-service eligibility shape. Administrator may name another Staff member via `creator_staff_id`, skipping these eligibility checks entirely (trusted to backfill/correct a historical record); a non-Administrator supplying `creator_staff_id` for anyone but themselves is rejected.

**The shared attachment infrastructure `03_DATABASE_MODEL.md` §1 deferred at Phase 0 is built now** — justified because Service Reports explicitly requires it and Phase 19 (Incident Reports) is the concrete, one-phase-away next consumer, satisfying DEC-018's "no premature abstraction" bar for a genuinely demonstrated second use. The shared `attachments` table uses a **typed, non-polymorphic ownership design** — never a Laravel-style `attachable_type` raw-PHP-class-name column paired with a bare `attachable_id` carrying no real foreign key (this codebase's established preference for typed references over generic polymorphism, DEC-017/DEC-038, applied to file ownership for the first time). `owner_type` (`App\Enums\AttachmentOwnerType`, one case today: `service_report`) is an explicit, closed discriminator, paired with a genuine, real, `NOT NULL`, `cascadeOnDelete()` foreign key **per owner type** — `service_report_id` — preserving full DB-level referential integrity while remaining trivially extensible: Phase 19 adds its own nullable `incident_report_id` column and its own enum case via an additive migration, never pre-added here speculatively. Storage goes through Laravel's filesystem abstraction via a single named `attachments` disk (`config('attachments.disk')`, `App\Support\Attachments\AttachmentDisk` — the sole point of access, mirroring `App\Support\CompanyTimezone`'s Phase 17 precedent); V1/local/test defaults to the framework's private `local` disk (never web-served, `02_ARCHITECTURE.md` §7's long-open production-provider question remains open — this phase resolves only what V1 actually needs, a swappable single-config-value abstraction, not a provider commitment). A conservative V1 allowlist (JPEG/PNG/PDF, 10 MB max, `config('attachments.php')`) is enforced by Laravel's content-sniffing `mimes` rule; antivirus/malware scanning is explicitly not a V1 commitment (`05_SECURITY_MODEL.md`'s File Uploads section, now implemented rather than aspirational). Attachment authorization always inherits the parent Service Report's own visibility for downloads; upload/removal is restricted to the creator/Administrator and only while the report is `draft`. Deleting a draft's attachments (individually, or via deleting the draft itself) removes the physical file via `App\Services\Attachments\AttachmentStorage` **before** the database row — file storage is outside the database transaction, so a crash between the two steps could in principle leave a dangling DB reference to an already-removed file, but never an orphaned file with no remaining database reference; this is the documented, accepted consistency boundary.

**Not introduced, per the governing Phase 18 instructions:** Flutter mobile UI, Admin Backoffice UI, offline data entry/synchronization, external/customer portal access or customer login (`00_PROJECT_CHARTER.md` rules out a public-facing client portal entirely — a barrier this phase's `site_representative_name` field, a plain text field with no signature capture, respects directly), digital signatures, PDF generation, printable report export, sequential report numbering, any Scheduler integration (no `ScheduleSourceType` addition, no fifth `/schedule` source, no automatic Schedule Entry ↔ Service Report creation in either direction, no Schedule Entry FK — the existing `service_appointment` `ScheduleEntryActivityType` value, added in Phase 17 with no forward link, remains independent until a future phase deliberately designs a real linking workflow), Notification integration (no new `NotificationType`/`NotificationSourceType` case), Messaging integration, parts/materials inventory or structured line items (narrative-only, per the governing instructions), labor/time tracking or GPS/location capture, multi-level approval (single-stage only, mirroring Leave, DEC-036), recurrence, or any background/queue/WebSocket infrastructure. `service_report_actions` is a scoped, per-module history table (DEC-010), not a stand-in for the still-unbuilt, project-wide Audit Logging concern (DEC-009).
**Rationale:** Client-as-required-anchor is the direct, minimal resolution of the governing instructions' explicit warning against turning Service Reports into a generic internal activity record — Project/Task optionality then follows DEC-006's already-validated precedent rather than inventing a new rule. A four-state workflow with `reviewed` as the sole final state is the smallest machine that satisfies "the roadmap's own review requirement" without importing a `completed` state that would have no distinct meaning for a report of already-finished work — collapsing "approved" and "completed" into one state avoids a distinction with no behavioral difference, the same discipline `ProjectMilestoneStatus` (deliberately smaller than `TaskStatus`) already applied in Phase 17. Rejecting a blanket `service-reports.view` permission and instead composing three already-validated row-level rules (manager-of-record, Project Lead, participant/creator ownership) keeps this phase's authorization surface exactly as small as CLAUDE.md §7 asks while matching the explicit, product-owner-articulated privacy stance that a Service Report's visibility should not be assumed to inherit Schedule Entries'/Tasks' broader Manager grant merely because the underlying mechanisms look similar. Building the shared attachment table now, with a typed real-FK-per-owner-type design rather than a fragile pseudo-polymorphic pair, is the direct application of this codebase's standing typed-reference preference to a genuinely two-phases-away consumer (Incident Reports) — the one case in this project where DEC-018's anti-premature-abstraction stance is outweighed by a concrete, documented, immediately-following second use, exactly the bar DEC-018 itself sets. Deleting physical files before the database row (rather than after) is the ordering that can only ever leave a dangling reference, never an orphaned file with no reference at all — the strictly safer failure mode given the instruction to never leave orphaned files.

### DEC-042 — Incident Reports: generic taxonomy, all-optional anchors, investigation-oriented lifecycle, narrower-than-Service-Reports visibility, and the shared attachment infrastructure's second consumer
**Date:** 2026-09-14
**Status:** ACCEPTED
**Decision:** Company App's V1 Incident Reports (Phase 19), preceded by a product-owner-reviewed planning audit (mirroring Phase 16/17/18's DEC-039/DEC-040/DEC-041 precedent) that resolved the roadmap's terse "Incident creation, assignment, action history, resolution" line into concrete architecture, is:

**Naming correction.** `03_DATABASE_MODEL.md`'s original Phase-0-era sketch used `incidents`/`incident_actions` — this phase instead uses the canonical `incident_reports`/`incident_report_actions`/`incident_report_participants` (`App\Models\IncidentReport`/`IncidentReportAction`), matching the product terminology "Incident Reports," Service Reports' own naming convention, and the `incident_report_id` attachment FK name DEC-041/the Phase 18 handoff already anticipated. `03_DATABASE_MODEL.md`'s stale `incidents`/`incident_actions` references are corrected, not silently left inconsistent.

**One generic entity, closed taxonomy.** `App\Enums\IncidentReportType` (`workplace_safety`/`client_site`/`operational`/`property_equipment_damage`/`it_security`/`other`) covers every incident category on one table/model — never dedicated tables/submodules per category, the same "all values of one generic entity" discipline `ScheduleEntryActivityType` (Phase 17) already established. `App\Enums\IncidentSeverity` (`low`/`medium`/`high`/`critical`, default `medium`) is a second, independent closed enum — no automatic severity/risk scoring was built.

**All three business anchors are optional — deliberately more permissive than Service Reports.** `client_id`/`project_id`/`task_id` are all nullable (`restrictOnDelete()`); an Incident Report may be entirely internal, with none of the three present. This is a genuine divergence from Service Reports' DEC-041 required-Client anchor, not an oversight — a Service Report exists only because billable client work occurred, while an incident (a workplace-safety event, an internal IT-security issue) frequently has no Client at all by nature. When Client/Project/Task are supplied, the same relational-coherence principle Service Reports established governs them (a supplied Project must not contradict a supplied Client; a supplied Task must not contradict Client/Project, with `project_id` server-derived from `task_id` when omitted) — implemented as a fresh `App\Http\Requests\IncidentReports\Concerns\ResolvesIncidentReportReferences` trait rather than a literal reuse of `ResolvesServiceReportReferences`, since Client's optionality would have forced that trait's "Client is always present" logic into an awkward branching mess rather than a clean shared abstraction (CLAUDE.md's "reuse only if it stays clean, never forced" instruction, applied literally).

**Occurrence is a genuine datetime, not a date.** `occurred_at` (UTC `datetime`) — deliberately unlike `service_reports.service_date` (date-only) — because an incident has a real moment of occurrence, not merely a calendar day. Returned as ISO-8601 UTC through the API; when company-timezone interpretation is needed, the existing `App\Support\CompanyTimezone` (Phase 17) is reused — no second timezone system was introduced. There is no separate `reported_at` — `created_at` already represents when the record was created, and (per the workflow below) `reported` is also the status assigned at creation, so no third timestamp would add information.

**Location is free text only.** A single nullable `location` string — no `locations` master-data table, no GPS/latitude/longitude/tracking of any kind, mirroring `staff_checkins.location_label`'s identical "free text, no catalog table, no tracking" precedent (Phase 9, DEC-005).

**Reporter and Assignment.** `reporter_staff_id` (required, `restrictOnDelete()`) is the Staff member whose report this is — immutable after creation at every status, mirroring `service_reports.creator_staff_id`'s standing-business-authority pattern. Administrator may name another Staff member via `reporter_staff_id` at creation (Work Log/Service Report's Administrator-on-behalf precedent, DEC-035/DEC-041); a non-Administrator supplying it for anyone but themselves is rejected. External/customer users can never be reporters (Company App has no external-person login concept; `00_PROJECT_CHARTER.md` rules out a public client portal). `assigned_to_staff_id` (nullable, `restrictOnDelete()`) is a single investigator — never a multi-investigator pivot — and is never accepted at creation (an incident may be reported unassigned); it is mutated only via dedicated `POST .../assign` (currently-unassigned only) and `POST .../reassign` (currently-assigned only) action endpoints, or bundled into `POST .../start-investigation` when entering investigation for the first time, so every change is always captured in `incident_report_actions` and can never be silently rewritten through a generic `PATCH`. Assignment authority is the reporter's *current* direct Manager (`Staff.manager_id`, evaluated live) or Administrator — never the reporter, never the assignee themselves, never an arbitrary Staff member.

**Participants and external persons.** `incident_report_participants` is a plain Staff pivot with no role/status hierarchy, no RSVP, no witness/injury-role enum — mirroring `service_report_participants` exactly; participation grants visibility only, never management authority. External/customer persons and witnesses are deliberately narrative-only (`people_involved`/`witness_notes` nullable text fields) — never structured tables, never linked to `Users`/`Contacts` (Company App has no external-person identity concept to link to).

**Narrative fields.** `description` (required at creation) plus nullable `immediate_action_taken`/`root_cause`/`corrective_action`/`preventive_action`/`follow_up_actions`/`resolution`/`people_involved`/`witness_notes` — validation-layer-bounded text, mirroring `service_reports`' narrative-field pattern. Investigation/resolution fields are deliberately not required at creation; they are filled progressively and gated only at the relevant workflow transition (see Resolution Requirements below).

**Workflow — an investigation-oriented lifecycle, deliberately NOT a copy of Service Reports' draft/submitted/reviewed/rejected shape.** `App\Enums\IncidentReportStatus`: `reported` → `under_investigation` → `resolved` → `closed`, plus an explicit `reopen` action (`resolved`|`closed` → `under_investigation`) — `reopened` is recorded only as an `IncidentReportAction` event, never persisted as a fifth status value. An incident must exist and be visible immediately upon reporting (safety/liability reasons favor prompt reporting over a draft-then-approve gate that Service Reports' model would have imposed) — there is no `draft`/`submitted`/`reviewed`/`rejected`/`approved`/`completed` state anywhere in this enum. `reported`/`under_investigation` are content- and attachment-mutable; `resolved`/`closed` are immutable for everyone, Administrator included — only `reopen` restores mutability. Every transition, and every assignment/reassignment, is an explicit action endpoint, never a generic status `PATCH` — mirroring the workflow-action discipline every prior phase with a lifecycle (Leave, Announcements, Service Reports) established.

**Workflow meaning and editing authority, per status:**
- **`reported`:** content-management authority is the reporter, the reporter's current Manager, the assigned investigator (if any), or Administrator.
- **`under_investigation`:** an assignee must already exist, or be supplied in the same `start-investigation` call (assignment authority applies to that bundled assignment specifically); content-management authority narrows to the assigned investigator, the reporter's current Manager, or Administrator — the reporter alone, without separately qualifying, is view-only.
- **`resolved`:** requires a non-empty `resolution` and at least one of `corrective_action`/`immediate_action_taken` (never `root_cause` universally) — validated against the *effective* value (this request's, or the record's existing one), mirroring `UpdateServiceReportRequest`'s "effective combination" pattern. Content and attachments become immutable.
- **`closed`:** the final state — closing authority is the assigned investigator, the reporter's current Manager, or Administrator. Content and attachments remain immutable.
- **`reopen`:** available from `resolved` or `closed`, same authority as investigation-management (assigned investigator/reporter's Manager/Administrator); restores editing/attachment capability to those same actors.

**Visibility — a tenth row-level shape, deliberately NARROWER than Service Reports' (DEC-041), no new permission.** Visible to: the reporter, the assigned investigator, listed participants, the reporter's current direct Manager, and Administrator. Unlike Service Reports, **a linked Project's Project Lead gains no automatic visibility or authority at all** merely from the Project link — Project Lead must separately qualify as reporter/assignee/participant/manager-of-record/Administrator. This is a deliberate, explicit product-owner instruction, not an oversight: Incident Reports' subject matter (safety, security, property/HR-adjacent events) is treated as more sensitive than Service Reports' routine client-work documentation, so the "Manager/Lead sees every Project-linked item" shape this codebase has used elsewhere (Schedule Entries, DEC-040) is composed even more narrowly here than Service Reports already narrowed it.

**Confidentiality was deliberately NOT built.** No `is_confidential` flag, no visibility enum, no HR-confidential/whistleblower/harassment-case workflow, no medical/injury-record subsystem, no workers'-compensation or regulatory (OSHA/DOLE-style) reporting. V1's narrow row-level visibility (reporter/assignee/participant/manager-of-record/Administrator, no broader Manager or Project Lead grant) is judged sufficient for the roadmap's actual scope; a dedicated confidential-case design remains a future, explicitly-requested decision, not something this phase should casually grow into.

**Deletion — historical-record retention, narrower than Service Reports.** Hard deletion is permitted only while an Incident Report is still `reported` **and** unassigned (`assigned_to_staff_id IS NULL`) — since entering investigation always changes status away from `reported`, this single condition captures "not yet assigned, not yet progressed into investigation" exactly. Deletion authority is the reporter or Administrator only — not the reporter's Manager, not an assigned investigator (there being none yet, in practice). Once assigned or investigated, an Incident Report is permanent operational history; resolution/closure are the only paths forward, never deletion, and Administrator has no bypass.

**Shared attachment infrastructure — the second authorized consumer, exactly as DEC-041 anticipated.** `App\Enums\AttachmentOwnerType::IncidentReport` (a new closed-enum case) pairs with a new nullable `incident_report_id` real FK (`cascadeOnDelete()`) on the existing `attachments` table — a purely additive migration, per DEC-041's own explicit design intent, never a redesign. Because a second owner type now exists, `attachments.service_report_id` — originally `NOT NULL` "since exactly one owner type exists today" — is widened to nullable in the same migration (every row now populates exactly one of the two owner FKs; no existing Service Report attachment row or behavior changes). `App\Support\Attachments\AttachmentDisk`/`App\Services\Attachments\AttachmentStorage` are reused as-is (the latter gains an optional directory-prefix parameter, defaulting to `'service-reports'` so every existing call site and stored path is unaffected; Incident Reports passes `'incident-reports'`); the same JPEG/PNG/PDF/10MB allowlist, private-disk-only storage, and generated-filename discipline apply unchanged. Attachment visibility always inherits the parent Incident Report's own (narrower) visibility; mutation is gated by both status (`reported`/`under_investigation` only) and the same content-management authority that gates the report's own content.

**Permissions.** No new permission was introduced — the old illustrative `incident.create`/`incident.assign`/`incident.resolve` catalog in `01_PRODUCT_REQUIREMENTS.md` §3 is explicitly non-authoritative (it predates every real permission this codebase has actually built, and its "assign" concept and singular `incident.*` naming match no established pattern); visibility/authority is resolved entirely in-controller (`App\Http\Controllers\Api\V1\IncidentReports\Concerns\AuthorizesIncidentReportAccess`), the same "no new permission, compose existing row-level rules" discipline Phases 16/17/18 established.

**Action history — append-only, assignment included.** `incident_report_actions` mirrors `service_report_actions`' exact structural shape (parent FK `cascadeOnDelete()`, `action` closed enum, nullable `acted_by_user_id`, optional `note`, no `public_id`). `App\Enums\IncidentReportActionType`: `reported`/`assigned`/`reassigned`/`investigation_started`/`resolved`/`closed`/`reopened`. Unlike Service Reports, the initial `reported` action is recorded by `IncidentReport`'s own model `created` event (not the controller) — a single source of truth ensuring every creation path (API, factory, a future seeder) produces a complete, accurate history, not merely the API path. An ordinary content `PATCH` is never logged as an action. This remains a scoped, per-module history table (DEC-010) — not a substitute for the still-unbuilt, project-wide Audit Logging concern (DEC-009).

**Not introduced, per the governing Phase 19 instructions:** Flutter mobile UI, Admin Backoffice UI, offline data entry/synchronization, external/customer incident submission or a customer portal, structured named-witness records, multi-investigator assignment, a confidentiality flag or any HR/harassment/whistleblower case-management workflow, a medical/injury-records subsystem, workers'-compensation workflow, regulatory (OSHA/DOLE-style) reporting, digital signatures, PDF generation, printable export, sequential incident numbering, Notification integration (no new `NotificationType`/`NotificationSourceType` case), Messaging integration, Scheduler integration (no `ScheduleSourceType` addition, no automatic Schedule Entry linkage), automatic Service Report creation, automatic Work Log creation, automatic Task mutation beyond the optional `task_id` FK itself, SLA/escalation timers, reminders, or any cron/queue/background-worker/Redis/WebSocket infrastructure. `incident_report_actions` is a scoped, per-module history table, not project-wide Audit Logging (DEC-009, still an unbuilt, pre-existing gap).

**Rationale:** An investigation-oriented lifecycle (reported/under_investigation/resolved/closed) is the smallest machine that matches how incidents actually unfold — reported promptly, investigated over time, then resolved and closed — rather than importing Service Reports' draft-then-approve shape, which would have wrongly gated an incident's very existence behind a submission step; DEC-010's own framing ("incident progress is a history, not a single mutable status field") directly supports append-only action history over a bare status column. Making Client/Project/Task all optional (rather than Service Reports' required-Client anchor) is the direct, minimal resolution of the product reality that an incident frequently has no external-facing anchor at all — treating this as a structural difference from Service Reports, not a smaller version of the same rule, avoids misrepresenting purely internal incidents as needing an artificial Client. Narrower visibility than Service Reports (no Project-Lead carve-out) is the direct, explicit product-owner instruction reflecting that incident subject matter is treated as more sensitive than routine client-work documentation — composing the existing manager-of-record/participant/ownership rules while deliberately declining to compose the Project-Lead rule is the same "reuse established shapes, but only where the product actually wants them" discipline DEC-041 itself modeled when it declined the Schedule Entries shape for Service Reports. Deliberately not building per-record confidentiality avoids speculatively growing this module into an HR case-management system on the strength of a single roadmap line — CLAUDE.md's scope-discipline principle applied directly; a real confidentiality requirement, if it emerges, deserves its own explicit decision and design, not a flag bolted on here. Reusing the shared attachment table via one additive migration (rather than a second parallel table) is exactly the "typed reference, real FK per owner type, trivially extensible" design DEC-041 built for this precise moment — the concrete second use that justified building it in Phase 18 in the first place.
