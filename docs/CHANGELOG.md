### 2026-09-12 — Phase 13: Leave Management
- **Backend:** added `leave_types` (configurable master data — `public_id` ULID, `name`, `code`, `description`, `is_paid`, `App\Enums\LeaveTypeStatus`, `sort_order`), `leave_requests` (`public_id` ULID, `staff_id`/`leave_type_id` both `restrictOnDelete()`, `start_date`/`end_date`, server-computed `total_days`, required `reason`, `App\Enums\LeaveRequestStatus`, `created_by_user_id` nullable/`nullOnDelete()`), `leave_request_actions` (append-only approval history — `leave_request_id` `cascadeOnDelete()`, `App\Enums\LeaveRequestActionType`, `acted_by_user_id` nullable/`nullOnDelete()`, `note`), and `leave_balances` (per-staff/per-type/per-calendar-year `allocated_days`; usage always derived live from `leave_requests`, never cached).
- Deliberately no `submitted_at`/`approved_at`/`rejected_at`/`cancelled_at` columns on `leave_requests` — submission is `created_at`, and every decision/cancellation timestamp lives only on `leave_request_actions` to avoid a dual-write risk between two sources of the same fact.
- Lifecycle: `pending` → `approved`/`rejected` (Administrator or the requester's current direct Manager only — a Manager can never approve/reject their own request or an unrelated Staff member's) → immutable; `pending`/`approved` → `cancelled` (requester, any time while `pending`, or only before `start_date` while `approved`; Administrator, any time). No arbitrary status `PATCH` — every transition is its own explicit action endpoint (`/approve`, `/reject`, `/cancel`). No edit endpoint exists at all — correcting a mistaken request means cancelling and resubmitting.
- Every Leave Request gets a `submitted` history row at creation (self-service or Administrator-entered); approve/reject/cancel each append their own row. A later `Staff.manager_id` change never rewrites who actually made a past decision.
- Leave Balances are per-staff/per-Leave-Type/per-calendar-year allocations with **derived, never cached** usage: `used_days` = approved requests' `total_days`, `pending_days` = pending requests' `total_days`, `remaining_days` = `allocated_days - used_days - pending_days`. A cancelled/rejected request contributes to neither sum, so cancelling a previously-approved request "restores" balance automatically with no explicit restoration code path. Unpaid Leave Types (`is_paid = false`) are never balance-checked at all (`allocated_days`/`remaining_days` report `null`, not `0`).
- Insufficient paid-leave balance is rejected at **submission time only** (never re-checked at approval), inside a database transaction with `lockForUpdate()` to prevent a concurrent-submission race; a Staff member with no `leave_balances` row yet is treated as `allocated_days = 0`.
- Self-service eligibility (checked only at creation, never re-validated): the requester's own Staff record must be `active`. Administrator-created requests (on a Staff member's behalf) deliberately skip this and the balance check — mirroring Phase 12's Work Log precedent — but Leave Type activity, date-range validity, and overlap are enforced identically for both creation paths.
- Overlapping `pending`/`approved` Leave Requests for the same Staff member are rejected regardless of Leave Type; `rejected`/`cancelled` requests never block. A request may not span two different calendar years. `total_days` is a plain inclusive calendar-day count — no business-day/holiday-aware calculation, weekends not excluded.
- `StaffController::destroy` (Phase 7) extended to reject deletion (`409`) while any Leave Request or Leave Balance references the Staff member, regardless of status. `LeaveTypeController::destroy` rejects deletion (`409`) while any Leave Request/Balance references the type — deactivation (`status: inactive`) is the tool for retiring one, and a deactivated type's existing Leave Requests remain fully intact.
- Four new permissions added to `RolePermissionSeeder`: `leave-types.view` (Administrator/Manager/Staff — company-wide, mirroring `organization.view`/`staff.view`), `leave-types.manage` (Administrator-only), `leave-requests.view` (**Manager only**, scoped in-controller to direct reports — mirroring Phase 12's `work-logs.view`, and also the permission checked alongside the manager-of-record relationship for approve/reject authority), `leave-requests.manage` (Administrator-only — create on behalf of a Staff member, Administrator-cancel).
- New versioned REST endpoints under `/api/v1`: `GET/POST /leave-types`, `GET/PUT/PATCH/DELETE /leave-types/{public_id}`; self-service `GET/POST /me/leave-requests`, `GET /me/leave-requests/{public_id}`, `POST /me/leave-requests/{public_id}/cancel`, `GET /me/leave-balances`; supervisory `GET /leave-requests`, `GET /leave-requests/{public_id}` (scoped in-controller — Administrator sees all, Manager sees direct reports), `POST /leave-requests` and `POST /leave-requests/{public_id}/cancel` (`leave-requests.manage`), `POST /leave-requests/{public_id}/approve`/`reject` (no permission middleware — row-level authority resolved in-controller); `GET/POST /staff/{public_id}/leave-balances` (scoped/`leave-requests.manage` respectively).
- `App\Http\Resources\LeaveRequestResource` exposes minimal `staff`/`leave_type`/`created_by` shapes plus a full `history` array (`LeaveRequestActionResource`) — no internal numeric ID anywhere.
- `LeaveTypeFactory`/`LeaveRequestFactory`/`LeaveBalanceFactory` added.
- Recorded DEC-036 (Leave Management domain model, lifecycle, approval/Manager authority, approval-history, balance, and historical-preservation decisions).
- Not payroll, salary deduction, statutory payroll computation, attendance, clock-in/clock-out, time tracking, Work Log integration, shift scheduling, roster planning, overtime, holiday pay, an automatic statutory leave-law engine, a tenure-based accrual engine, carry-forward, encashment, medical-document attachments, multi-level/delegated approval, calendar sync, notifications, or leave/staffing forecasting; no partial-day/half-day leave; no Admin Backoffice CRUD UI or Flutter mobile screens (consistent with Phase 6–12's precedent).

### 2026-09-12 — Phase 12: Work Logs
- **Backend:** added `work_logs` table; `App\Models\WorkLog`, with a ULID `public_id` (DEC-017). Duration model (not start/end timestamps): `work_date` (required, `before_or_equal:today`), `duration_minutes` (required positive integer, `max:1440`), `description` (required, `max:2000`).
- A Work Log optionally references a `task_id` and/or a `project_id` — never neither. When `task_id` is set, `project_id` is server-derived from the Task's own Project (which may itself be `null` for an independent Task) and a client-supplied `project_id` alongside `task_id` is rejected outright — task↔project inconsistency (`Work Log.project = A` while `Work Log.task` belongs to Project B) is structurally impossible, not merely validated.
- `staff_id` (required, `restrictOnDelete()`) is the performer; `created_by_user_id` (nullable, `nullOnDelete()`) is accountability metadata only, mirroring `tasks.created_by_user_id` (Phase 11) — kept deliberately distinct from the performer.
- Self-service creation eligibility (checked only at creation, never re-validated): the performer's own Staff record must be `active`; for a Project-linked Task or a direct Project reference, the performer must currently be a Project member (**any** role, not only the Task's assignee); for an independent Task, the performer must be that Task's current assignee. Administrator-entered Work Logs (naming another Staff member) deliberately skip this eligibility check — an Administrator is trusted to backfill/correct a record for a Staff member who may since have left a Project or become inactive.
- Historical preservation: removing a Project Membership, reassigning a Task, a Staff member becoming inactive/separated, or a Task completing/being cancelled never alters or removes an existing Work Log — eligibility is a creation-time gate only, and new Work Log creation is **not** gated by Task status at all.
- `TaskController::destroy`/`ProjectController::destroy`/`StaffController::destroy` (Phases 11/10/7) extended to also reject deletion (`409`) while a Work Log references them.
- Editing/deletion: the performer may edit (`work_date`/`duration_minutes`/`description` only) or hard-delete their **own** Work Log at any time — no arbitrary time-window restriction. An Administrator (`work-logs.manage`) may correct or delete **any** Work Log, with the same field restriction — `staff_id`/`task_id`/`project_id` are immutable for everyone after creation, including Administrator (a wrongly-attributed Work Log is deleted and recreated instead of reassigned). No Project Lead or Manager edit/delete authority exists anywhere in this module — deliberately stricter than Tasks.
- Two new permissions added to `RolePermissionSeeder`: `work-logs.view` (**Manager only**, scoped in-controller to the Manager's own direct reports — mirroring Phase 9's `location.view` precedent, not Phase 10/11's company-wide Manager grant, since logged work duration/timing is treated as materially more sensitive than the Staff/Task/Project directories) and `work-logs.manage` (Administrator-only). A Project Lead's read-only visibility into their led Projects' Work Logs is a row-level, in-controller check (`App\Http\Controllers\Api\V1\WorkLogs\Concerns\AuthorizesWorkLogVisibility`), not a permission.
- New versioned REST endpoints under `/api/v1`: self-service `GET`/`POST /me/work-logs`, `PUT`/`PATCH`/`DELETE /me/work-logs/{public_id}` (performer identity always server-derived from the authenticated User's linked Staff record, never client-supplied — reuses Phase 9's `RequiresLinkedStaff` precedent; a `public_id` belonging to another Staff member returns `404`, not `403`, since its existence is itself sensitive); supervisory/administrative `GET /work-logs`, `GET /work-logs/{public_id}` (scoped in-controller — Administrator sees all, Manager sees direct reports, Project Lead sees led-Project logs read-only), `POST`/`PUT`/`PATCH`/`DELETE /work-logs...` (`work-logs.manage`, Administrator-only).
- `App\Http\Resources\WorkLogResource` exposes minimal `staff`/`task`/`project`/`created_by` shapes only — no internal numeric ID, no raw `User` identity for the creator.
- `WorkLogFactory` added.
- Recorded DEC-035 (Work Logs domain model, performer/creator distinction, eligibility, historical-preservation, and authorization decisions).
- No payroll, salary/overtime calculation, billable rates, invoicing/client billing, attendance, clock-in/clock-out, geolocation/background tracking, timers, timesheet approval workflow, weekly timesheet submission, payroll-period locking, utilization analytics, productivity/performance scoring, leave/holidays/shift scheduling, comments/messaging/notifications/reminders/attachments, or Project financials was introduced; no Admin Backoffice CRUD UI or Flutter mobile screens (consistent with Phase 6–11's precedent).

### 2026-09-11 — Phase 11: Tasks
- **Backend:** added `tasks` table; `App\Models\Task`, with a ULID `public_id` (DEC-017). `App\Enums\TaskStatus` (`todo`/`in_progress`/`blocked`/`completed`/`cancelled`); `App\Enums\TaskPriority` (`low`/`normal`/`high`/`urgent`, default `normal`).
- Honors DEC-006 (Phase 0): `tasks.project_id` is **nullable** (`restrictOnDelete()`) — a Task may exist independently of a Project, not only within one. A single nullable `assignee_staff_id` (`restrictOnDelete()`) is used, not a `task_assignees` many-to-many pivot — resolves `03_DATABASE_MODEL.md`'s open question in favor of the smallest V1 model. `created_by_user_id` (nullable, `nullOnDelete()`) is accountability metadata only, never an authorization primitive.
- New-assignment eligibility mirrors Project Membership (Phase 10): only `active` Staff (Phase 7) may be newly assigned, and — when the Task belongs to a Project — the assignee must currently be a member of that Project (server-enforced). Because assignment references `staff_id` directly rather than through Project Membership, **removing a Project Membership never disturbs an existing Task assignment** — assignment history is preserved, exactly as Phase 10's own handoff anticipated; an assignee's later `inactive`/`separated` employment status likewise never disturbs an existing assignment.
- `completed_at` is server-controlled only (both Form Requests reject a client-supplied value): set to `now()` on transition to `completed`, cleared when a completed Task is reopened — deliberately different from Project's user-supplied, reopen-preserved `completed_date`.
- `ProjectController::destroy`/`StaffController::destroy` (Phases 10/7) extended to also reject deletion (`409`) while a Task still references them; Staff deletion is blocked regardless of the referencing Task's status. A Task's own `DELETE` is Administrator-only and permitted only while the Task is still `todo` — anything with real activity must be retired via `PATCH .../{public_id}` with `status: cancelled` instead, preserving history rather than destroying it.
- Two new permissions added to `RolePermissionSeeder`: `tasks.view` (**Manager only**, mirroring `projects.view`) and `tasks.manage` (Administrator-only). No `tasks.assign`/`tasks.complete`/`tasks.delete` granular permissions were introduced.
- `App\Http\Controllers\Api\V1\Tasks\Concerns\AuthorizesTaskAccess` extends Phase 10's row-level visibility pattern to **writes** for the first time in this codebase: a Project Lead (`ProjectMembershipRole::ProjectLead` on the Task's own Project) may create/update Tasks scoped strictly to that Project — a bounded, Task-specific authorization decision, not a retroactive grant of `projects.manage`; a Task's assignee may update only its `status` field (self-service), enforced by diffing the validated payload's keys, not a new permission. Visibility: `tasks.view` holders see every Task; otherwise a linked-Staff requester sees Tasks in Projects they belong to (any role) plus any Task assigned to them directly — never broader than the equivalent Project's own visibility.
- New versioned REST endpoint under `/api/v1`: `tasks` — a **flat, top-level resource** (filterable by `?project=`/`?status=`/`?assignee=`/`?priority=`/`?q=`), not nested under `/projects/{project}/tasks` — full CRUD, route-model-bound by `public_id`. `GET`/`POST`/`PUT`/`PATCH` carry no `can:<permission>` route middleware at all (authority resolved entirely in-controller); `DELETE` remains a conventional `can:tasks.manage` route.
- `App\Http\Resources\TaskResource` exposes minimal `project`/`assignee`/`created_by` shapes only — no internal numeric ID, no raw `User` identity for the creator (only a linked Staff's minimal shape, or `null`).
- `TaskFactory` added.
- Recorded DEC-034 (Tasks domain model, assignee eligibility, Project Lead/assignee authorization, and delete-behavior decisions).
- `docs/ROADMAP.md`'s Phase 11 description is narrowed: task comments, mentioned there, were not part of the governing Phase 11 instructions for this session and remain unimplemented — deferred to a future collaboration phase alongside Work Logs/task activity/notifications (the same kind of scope note Phase 10 recorded for Project milestones).
- No work logs, time tracking, timers, timesheets, billable hours, payroll, attendance, task comments/attachments/reactions, messaging, notifications, mentions, Kanban boards, configurable workflows, subtasks, task dependencies, recurring tasks, calendars, reminders, Gantt charts, milestones, resource forecasting, project budgeting/financials, utilization metrics, task activity timeline, audit/event stream, or approval workflows was introduced; no Admin Backoffice CRUD UI or Flutter mobile screens (consistent with Phase 6/7/8/9/10's precedent).

### 2026-09-11 — Phase 10: Projects & Project Membership
- **Backend:** added `projects` and `project_memberships` tables; `App\Models\Project`/`ProjectMembership` (`projects` carries a ULID `public_id`, DEC-017; `project_memberships` deliberately doesn't — never independently addressed by URL). `App\Enums\ProjectStatus` (`planned`/`active`/`on_hold`/`completed`/`cancelled`) is a single lifecycle mechanism; `App\Enums\ProjectMembershipRole` (`project_lead`/`member`) is a project-scoped responsibility, distinct from the global Administrator/Manager/Staff application role.
- No `project_manager_staff_id` column — leadership is expressed entirely through Project Membership's `role`, avoiding two competing sources of truth.
- `projects.client_id` is nullable (`restrictOnDelete()`) — a Project may be internal, or optionally belong to one Client; an inactive Client neither loses its existing Projects nor is blocked from receiving new ones.
- `project_memberships` (`project_id`/`staff_id`, both `restrictOnDelete()`, unique on the pair) represents the *current* roster only — no historical-period tracking; removal is a hard delete. Only `active` Staff (Phase 7) may be newly assigned; existing memberships survive a later employment-status change.
- `ClientController`/`StaffController::destroy` (Phases 8/7) extended to also reject deletion (`409`) when a Project/Project Membership still references the Client/Staff member; `ProjectController::destroy` rejects deletion while any Project Membership exists.
- Two new permissions added to `RolePermissionSeeder`: `projects.view` (**Manager only** — the first `*.view` permission not also granted to Staff) and `projects.manage` (Administrator-only, covering Project CRUD and all Project Membership writes).
- An ordinary Staff member holds neither permission — Project visibility is instead scoped in-controller (`App\Http\Controllers\Api\V1\Projects\Concerns\AuthorizesProjectVisibility`) to Projects where their linked Staff record holds a Project Membership, applied directly to the primary `GET /api/v1/projects`/`{public_id}` endpoints (the second real row-level authorization pattern in this codebase, after Phase 9's Manager→direct-reports scoping, and the first to apply to a primary resource rather than a `/me/...` or secondary endpoint).
- New versioned REST endpoints under `/api/v1`: full CRUD for `projects`, route-model-bound by `public_id`, filterable by `status`/`client`/`member`/`q`; nested `GET`/`POST /projects/{public_id}/members`, `PUT`/`PATCH`/`DELETE /projects/{public_id}/members/{staff_public_id}` (the first genuinely nested resource with real endpoints in this API, addressed by the member's Staff `public_id`).
- `App\Http\Resources\ProjectResource` exposes a `members_count` (not a nested roster) and the requester's own `my_role`; `App\Http\Resources\ProjectMembershipResource` nests a minimal Staff identity only.
- `ProjectFactory`/`ProjectMembershipFactory` added.
- Recorded DEC-033 (Projects & Project Membership domain model, membership-based leadership, and scoped-visibility decisions).
- Found and fixed one real routing bug during this phase's own test run: Laravel's automatic nested-route-binding scoping (triggered by two consecutive `:public_id`-bound Eloquent route parameters) guessed a nonexistent `Project::staff()` relation for the member-update/remove routes; fixed via `->withoutScopedBindings()` since membership is already verified explicitly in the controller.
- No tasks, task assignment, subtasks, Kanban, task comments/dependencies, work logs, time tracking, timesheets, payroll, billing, project invoicing, quotations, contracts, CRM opportunity pipelines, file/document management, messaging, notifications, calendars, Gantt charts, resource forecasting, project budgeting/financials, utilization metrics, project profitability, performance scoring, or approval workflows was introduced; no Admin Backoffice CRUD UI or Flutter mobile screens (consistent with Phase 6/7/8/9's precedent).

### 2026-09-11 — Phase 9: Staff Status & Location Check-in

- Both tables are append-only history; "current" status/location is a derived read (`Staff::latestOperationalStatus()`/`latestCheckIn()`, `latestOfMany()`), not a denormalized mutable column — a staff member with no history has `null` current status/location, never an assumed default.

- New versioned REST endpoints under `/api/v1`: `GET`/`POST /me/status`, `GET`/`POST /me/check-ins` (self-service, requiring the authenticated User to have a linked Staff record — `403` otherwise, no new permission); `GET`/`POST /staff/{public_id}/status`; `GET /staff/{public_id}/check-ins`; `DELETE /check-ins/{public_id}`. "Updating" status/creating a check-in is modeled as appending to the same paginated, latest-first list the `GET` returns.
- `App\Http\Resources\StaffResource` gains `operational_status` (nullable) — no location data of any kind was added to it.
- `StaffOperationalStatusFactory`/`StaffCheckInFactory` added.

### 2026-09-11 — Phase 8: Clients & Contacts
