### 2026-09-23 — Phase 26 Gate 2F: D-1 fix — Android release builds lacked the INTERNET permission
- **Defect D-1 (discovered during Gate 2F pre-UAT validation, before any UAT scenario was run):** `apps/mobile/android/app/src/main/AndroidManifest.xml` did not declare `android.permission.INTERNET`; only `src/debug/` and `src/profile/` did (the Flutter template default since Phase 1). Release builds merge only `main` plus library manifests, so every Android release build had no network access and every API call (login, session restore, logout) would fail with "Could not reach the server". Debug builds (`flutter run`) masked the defect.
- **Evidence (product owner's Windows machine, baseline `b3c80bc`, Flutter 3.47.2):** `flutter build apk --release` succeeded; `aapt2 dump permissions app-release.apk` listed only `com.companyapp.mobile.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` (an AndroidX-internal signature permission); all three merged release manifests showed the same single `uses-permission`. No library contributes `INTERNET` through manifest merging.
- **Fix:** one line, `<uses-permission android:name="android.permission.INTERNET" />`, at manifest scope before `<application>` in the main manifest, so all build variants inherit it. No `usesCleartextTraffic`, network-security config, TLS/certificate change, API-URL change, authentication change, dependency change, or `debug`/`profile` manifest change. Android 9+ still blocks cleartext HTTP by default.
- **UAT:** unchanged — UAT-25-01…04 and UAT-26-01…04 remain `NOT RUN`. The staging release APK build and real-device UAT follow after this fix merges.

### 2026-09-14 — Phase 22: Security Audit
- Delivered in two authorized steps. First, a repository inspection/audit-only session produced an evidence-based, code-verified security audit (`docs/phases/V1_PHASE_22_SECURITY_AUDIT.md`) covering authentication, authorization/IDOR, input validation/injection, file uploads, secrets/configuration, logging, CI/CD, dependencies, and the Flutter mobile client — **no Critical or High findings**. The product owner then explicitly authorized a narrow remediation scope (recorded as DEC-045), not the full hardening list the audit enumerated.
- **F-01 (required fix):** `AuthController::login` (API) and `LoginForm::login` (Admin) previously returned a distinguishable message ("This account is not currently active...") for a suspended/inactive account authenticated with the *correct* password, versus the generic message for wrong credentials — itself disclosing account existence/status to anyone holding valid credentials for it, and contradicting `05_SECURITY_MODEL.md`'s own no-enumeration guarantee. Both failure paths now return the identical generic message on both surfaces. Account-status enforcement (`User::isActive()`/`EnsureAccountIsActive`) is unchanged; the specific reason is preserved only internally, as a curated `reason` field on the existing `auth.login_failed` audit entry (Administrator-only).
- **F-02:** `config('sanctum.expiration')` is now `env('SANCTUM_EXPIRATION', 43200)` (30 days) instead of `null` (never), using Sanctum's own built-in expiration mechanism — no refresh-token architecture introduced. Bounds the standing blast radius of a lost/stolen mobile device's bearer token.
- **F-03 investigated and dropped, not a gap:** the audit's own optional, lowest-priority "add a defense-in-depth check to `WorkLogController`" item was confirmed unnecessary on inspection — `RolePermissionSeeder` never attaches `work-logs.manage` to Manager/Staff, so the existing `can:work-logs.manage` route middleware (Administrator-only) already fully protects every write action. - Two new permissions added to `RolePermissionSeeder`: `tasks.view` (**Manager only**, mirroring `projects.view`) and `tasks.manage` (Administrator-only). No `tasks.assign`/`tasks.complete`/`tasks.delete` granular permissions were introduced.
