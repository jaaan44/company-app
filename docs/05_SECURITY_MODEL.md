## Admin Dashboard & Reporting Aggregation (Phase 20, DEC-043)

**Implemented as of Phase 20: no new permission at all** — `dashboard.view`/`reports.view` and any per-resource equivalent were considered and rejected, continuing the unbroken Phase 16–19 precedent of composing existing row-level rules rather than adding a blanket permission. The governing rule is explicit and absolute: **Dashboard/Report aggregation must never widen the visibility a source module's own endpoint already grants a requester — including aggregate counts with no drill-down.** There are no coarse-count exceptions. Every Dashboard section and every Report resource is scoped by a dedicated `App\Services\Reporting\*Visibility` class (`StaffVisibility`, `ClientVisibility`, `ProjectVisibility`, `TaskVisibility`, `WorkLogVisibility`, `LeaveRequestVisibility`, `ServiceReportVisibility`, `IncidentReportVisibility`) that reuses — via `use` of the source module's own existing authorization trait — that trait's pure, non-aborting predicates, reproducing the identical composed visibility rule as a query rather than a per-instance check (the same adaptation `ScheduleController` established in Phase 17 for its own cross-module aggregation), so a requester can never learn more through `/dashboard` or `/reports/...` than they could already learn by paging through `GET /api/v1/{source}` itself. No existing source-module trait or controller was modified to build this — every one of Phases 7–19's own authorization surfaces is unchanged.

Incident Reports receives particular emphasis: the reused rule carries **no Project-Lead carve-out**, exactly mirroring Phase 19's own deliberate narrowing (DEC-042) — a Project Lead gains no Incident Report visibility through Dashboard or Reports merely because a linked Project exists, precisely as they gain none through `GET /api/v1/incident-reports` itself. Service Reports' own (already narrower-than-Scheduler) visibility is likewise reused exactly, with its Project-Lead carve-out intact only because that carve-out exists in the source rule itself.

Work Logs and Leave Requests' Reporting services each add one documented, narrow fallback beyond their source trait's own supervisory-only rule: a plain Staff member with none of the supervisory access tiers (Administrator/Manager-of-direct-reports/Project-Lead) still sees their **own** records — exactly what they already see via `GET /api/v1/me/work-logs`/`/me/leave-requests`. This is not a widening; it reflects visibility those two source modules already grant through a *different* existing route.

CSV export inherits the identical scoping as its JSON counterpart — no export ever returns a row, or reveals a count, beyond what the same requester's `GET /api/v1/reports/{resource}` would already show. See `docs/phases/V1_PHASE_20_DEFINITION.md` and DEC-043 for the full Dashboard/Report specification.

## Authentication

- **Implemented (DEC-022):** the Admin Backoffice authenticates via Laravel's session/secure-cookie `web` guard (Blade + Livewire login). The Flutter mobile app authenticates via Laravel Sanctum personal access tokens (`Authorization: Bearer <token>`) — bearer-token only, no cookie-based SPA/stateful authentication. No OAuth server, JWT infrastructure, or Passport.
- Passwords hashed with Laravel's default facilities (bcrypt, `password` cast to `hashed`) — never rolled by hand, never logged, never returned in any response (`UserResource` exposes only `public_id`, `name`, `email`, `status`).
- **Implemented:** rate limiting on both login surfaces — see Rate Limiting below.
- **No public self-registration (DEC-023):** no `POST /register` route on either surface; accounts are company-provisioned.
- **Not implemented (deliberately deferred):** password reset and email verification workflows. `email_verified_at` is retained on `users` for future use but nothing populates or checks it yet.
- **Implemented as of Phase 22 (Security Audit, F-01):** a login failure returns the identical generic message ("These credentials do not match our records.") whether the email doesn't exist, the password is wrong, **or the matched account is suspended/inactive** — on both `AuthController::login` (API) and `LoginForm::login` (Admin). Earlier phases already avoided disclosing account existence for a wrong password/unknown email, but returned a distinct "this account is not currently active" message for a suspended/inactive account with a correct password — itself an account-existence/status disclosure to anyone holding valid credentials for it, found and closed by the Phase 22 audit (`docs/phases/V1_PHASE_22_SECURITY_AUDIT.md`, finding F-01). Enforcement is unchanged (`User::isActive()`/`EnsureAccountIsActive` still block the account exactly as before); only the externally-visible message no longer distinguishes the two failure reasons. The specific reason is preserved internally as a curated `reason` field (`invalid_credentials`/`inactive_account`) on the existing `auth.login_failed` audit entry (Administrator-only, see Audit Logging below) — this is not a new audited field type, just an additional curated value on an event already audited since Phase 21.
- **Implemented as of Phase 22 (Security Audit, F-02):** mobile Sanctum tokens now expire after `config('sanctum.expiration')` — 43,200 minutes (30 days) by default, overridable via `SANCTUM_EXPIRATION` — instead of never. This uses Sanctum's own built-in expiration check (`Laravel\Sanctum\Guard::isValidAccessToken()`, comparing a token's `created_at` against `now()->subMinutes($expiration)`); no refresh-token architecture was introduced. A device that goes 30+ days without a request simply requires the user to log in again, exactly like any other expired-token flow. This bounds the standing blast radius of a lost/stolen device that this document previously flagged as an open item (see the superseded note under API Access below).

## Authorization

- **Permission-oriented, not purely role-hardcoded** (DEC-004). Every protected action checks a specific permission (e.g. `leave.approve`), not just "is this user an Administrator."
- Roles are named bundles of permissions for manageability, not the authorization primitive itself.
- **Implemented as of Phase 5 (DEC-028):** `roles` (`Administrator`/`Manager`/`Staff`, a fixed V1 catalog), `permissions` (dot-notation identifiers), and a many-to-many `role_permissions` join. **One role per user** — `users.role_id`, nullable — not a many-to-many `users`↔`roles` table; a user with no role has no permissions (default-deny).
  - **Centralized enforcement:** a single `Gate::before` callback (`App\Providers\AppServiceProvider::boot()`) is the one place Administrator's "may do everything" behavior is expressed — not `if ($user->is_admin)`/`if ($user->role === 'admin')` checks scattered through controllers, Livewire components, or Blade views. Every other user's ability check resolves against their role's attached permissions via `App\Models\User::hasPermission()`.
  - **Reusable across every Laravel authorization surface:** because this is a real `Gate::before` override (not a bespoke helper function), Laravel's built-in `can` route middleware, `Gate::allows()`/`authorize()`, Blade's `@can`, and `$user->can()`/`$user->cannot()` inside a future Policy all work against permission names with zero per-permission `Gate::define` boilerplate. A future developer protects a new action by asking "does Laravel already have a mechanism for this surface (route, Blade view, Policy method)?" and calling `can('module.action')` through it — not by inventing a new check.
  - **Foundational permission catalog only** — `admin.access`, `authorization.manage` — enough to prove the mechanism; each future module's permissions arrive with that module, not speculatively here (CLAUDE.md §7).
  - Manager and Staff hold **no permissions** as of Phase 5 — acceptable (CLAUDE.md §10); this is not a gap, it's the correct default-deny starting state until real modules attach real permissions to these roles.
  - **Implemented as of Phase 6 (DEC-029):** `organization.view`/`organization.manage` (Departments/Teams/Positions) — the first real permissions attached to Manager/Staff (`organization.view` only; viewing the company's org structure is low-sensitivity company metadata). `organization.manage` (create/update/delete) remains Administrator-only via the same centralized override — no new authorization mechanism was introduced.
  - **Implemented as of Phase 7 (DEC-030):** `staff.view`/`staff.manage` (the Staff Directory) — same pattern: `staff.view` attached to Manager/Staff (the directory is company-wide, not admin-only), `staff.manage` Administrator-only. The linked User account's own identity within a Staff record's response is additionally gated behind `staff.manage` specifically (see API Access below) — a finer-grained distinction than a bare permission check, applied at the resource-shaping layer.
  - **Implemented as of Phase 8 (DEC-031):** `clients.view`/`clients.manage` (Clients & Contacts) — same pattern: `clients.view` attached to Manager/Staff (the directory is company-wide), `clients.manage` Administrator-only. Contacts share these same permissions rather than a separate `contacts.*` pair — a Contact has no independent meaning apart from its Client, keeping the permission catalog as small as CLAUDE.md's Phase 8 instructions ask.
  - **Implemented as of Phase 9 (DEC-032):** `staff-status.view`/`staff-status.manage` (operational status) and `location.view`/`location.manage` (location check-ins). `staff-status.view` is attached to Manager/Staff (company-wide — a status word is low-sensitivity); `staff-status.manage` (correcting another staff member's status) is Administrator-only. `location.view` is attached to **Manager only**, not Staff, and — unlike every permission before it — holding the permission is not by itself sufficient: `CheckInController` additionally scopes a non-Administrator holder to their own direct reports (`Staff.manager_id`). `location.manage` (deleting/correcting a check-in) is Administrator-only.
  - **Implemented as of Phase 10 (DEC-033):** `projects.view`/`projects.manage`. `projects.view` is attached to **Manager only** — the first `*.view` permission in this codebase not also granted to Staff, since Projects may carry sensitive client-engagement information, unlike the company-wide Staff/Client/Organization directories. `projects.manage` (Project CRUD and all Project Membership writes — add/change-role/remove) remains Administrator-only, same pattern as every prior `*.manage` permission; no project-lead self-management carve-out was introduced. An ordinary Staff member holds neither permission and instead sees only Projects where their linked Staff record holds a Project Membership (see Data isolation below).
  - **Implemented as of Phase 11 (DEC-034):** `tasks.view`/`tasks.manage`, following `projects.view`'s precedent exactly — `tasks.view` is **Manager only**; `tasks.manage` is Administrator-only, covering unrestricted Task CRUD. No `tasks.assign`/`tasks.complete`/`tasks.delete` granular permissions were added. Instead, a Project Lead's Task-management authority (scoped strictly to Tasks in a Project where their linked Staff record holds `ProjectMembershipRole::ProjectLead`) and a Task assignee's status-only self-service are both enforced as row-level, in-controller checks (`App\Http\Controllers\Api\V1\Tasks\Concerns\AuthorizesTaskAccess`) — the first time this codebase scopes *write* authority (create/update), not only reads, outside the permission system. Neither carve-out expands `tasks.manage`, `projects.manage`, or the `project_lead` Project Membership role into any broader authority.
  - **Implemented as of Phase 12 (DEC-035):** `work-logs.view`/`work-logs.manage`. Unlike `tasks.view`/`projects.view`, `work-logs.view` is attached to **Manager only** and is further scoped in `WorkLogController` to the Manager's own direct reports (`Staff.manager_id`) — mirroring `location.view`'s Phase 9 precedent, not a company-wide grant, since logged work duration/timing is treated as materially more sensitive than the Staff/Task/Project directories. `work-logs.manage` is Administrator-only, covering create-for-others/edit-any/delete-any. A Project Lead's **read-only** visibility into Work Logs within Projects they lead is a row-level, in-controller check (`App\Http\Controllers\Api\V1\WorkLogs\Concerns\AuthorizesWorkLogVisibility`), not a permission — and, deliberately unlike Phase 11's Task authority, grants **no** edit/delete/create-for-others authority at all. Self-service (`/me/work-logs`) needs no permission, mirroring Phase 9's domain-check pattern.
  - **Implemented as of Phase 13 (DEC-036):** four permissions. `leave-types.view` follows `organization.view`/`staff.view`'s company-wide pattern (Administrator/Manager/Staff — a Staff member must browse active Leave Types to submit a request); `leave-types.manage` is Administrator-only. `leave-requests.view` mirrors `work-logs.view`'s Phase 12 shape exactly: **Manager only**, further scoped in `LeaveRequestController`/`LeaveBalanceController` to the Manager's own direct reports — and, unlike every prior `*.view` permission, is also one of the two conditions (alongside being the requester's current direct Manager) checked for **approve/reject authority**, the first time a `*.view` permission doubles as part of a write-authority check in this codebase. `leave-requests.manage` is Administrator-only (create a Leave Request on a Staff member's behalf; Administrator-cancel any request; set/update Leave Balance allocations). Approve/reject themselves carry **no** permission route middleware at all — authority is resolved entirely in-controller (Administrator, or the requester's current direct Manager — never the requester themselves, even defensively), the same row-level write-authority shape Phase 11 (Project Lead) and Phase 12 established, now applied to an explicit two-party approval decision rather than a single actor's own records. Self-service (`/me/leave-requests`, `/me/leave-balances`) needs no permission, mirroring Phase 9/12's domain-check pattern.
  - **Implemented as of Phase 14 (DEC-037):** a single permission, `announcements.manage` — Administrator-only, gating the **entire** management surface (reads and writes alike). Unlike every prior module, there is deliberately **no** companion `announcements.view`: a Manager holds no elevated Announcement authority of any kind — they read their own targeted feed exactly like any Staff member, via `/me/announcements` (a domain check — a linked Staff record — needing no permission, mirroring Phase 9/12/13's self-service pattern).
  - **Implemented as of Phase 16 (DEC-039):** **no new permission at all** — `messages.view`/`messages.manage` were considered and rejected, mirroring Phase 15's identical choice for Notifications. Messaging visibility/authority is membership/ownership-only, enforced entirely in `App\Http\Controllers\Api\V1\Messaging\Concerns\AuthorizesConversationAccess`, which never calls `$user->can(...)` — so Administrator's centralized `Gate::before` override (DEC-028) is never invoked for any Messaging endpoint, the second such case in this codebase after Notifications. A group conversation's owner-only member-management authority and the owner-cannot-leave-while-others-remain invariant are both row-level, in-controller checks (`ConversationMemberController`), not permissions — the same "authority resolved entirely in-controller" shape Phase 11–13 established for Project Lead/Work Log/approval authority, now applied to a peer-to-peer (not hierarchical) relationship for the first time.
  - **Implemented as of Phase 17 (DEC-040):** **no new permission at all** — `schedule.view`/`schedule.manage` were considered and rejected, per the governing Phase 17 instructions' explicit direction to prefer established row-level patterns over a blanket permission that would expose private entries. Schedule Entry visibility/authority (`App\Http\Controllers\Api\V1\Scheduling\Concerns\AuthorizesScheduleEntryAccess`) mirrors `AuthorizesTaskAccess`'s shape (DEC-034) exactly: Administrator (a direct `hasRole()` check) sees/manages everything; otherwise a Staff-linked requester may view an entry they created, one they participate in, or one linked to a Project their *existing* Project visibility (`AuthorizesProjectVisibility`, reused as-is) already allows; manage authority is the creator, the linked Project's Project Lead, or Administrator, with a mere participant strictly read-only. **A Manager gains no automatic visibility into a direct report's private (non-Project-linked) Schedule Entry merely from the manager relationship** — a deliberate departure from Work Logs'/Leave's Manager-of-direct-reports scoping (DEC-035/DEC-036), since a personal calendar entry is treated as more private than logged work or a leave reason. Project Milestone authorization (`AuthorizesMilestoneAccess`) reuses `AuthorizesProjectVisibility` as-is for reads and the existing `projects.manage` permission (already unconditionally granted to Administrator via `Gate::before`) plus a Project Lead carve-out for writes — requiring no new permission at all. The unified `GET /api/v1/schedule` aggregation preserves each source's own existing visibility rule exactly (Task/Milestone via a self-contained, non-aborting replica of their established rules; Leave via `AuthorizesLeaveRequestVisibility`'s rule plus a Staff member always seeing their own approved leave, mirroring their existing `/me/leave-requests` access) — never a blanket company-wide calendar.
  - **Implemented as of Phase 18 (DEC-041):** **no new permission at all** — `service-reports.view`/`.manage` were considered and explicitly rejected by the product owner, since a blanket `service-reports.view` would grant every Manager company-wide visibility. `App\Http\Controllers\Api\V1\ServiceReports\Concerns\AuthorizesServiceReportAccess` resolves visibility entirely in-controller: a Service Report is visible to its creator, its participants, the creator's *current* direct Manager (`Staff.manager_id`, a plain relationship check — mirroring `AuthorizesLeaveRequestVisibility`'s `isDirectManagerOf()` shape, never a `*.view` permission grant), the linked Project's Project Lead (reusing the established `ProjectMembership` check), or Administrator (a direct role check). **Deliberately narrower than Schedule Entries' model (DEC-040):** a Manager holding `projects.view` does **not** automatically see every Project-linked Service Report — only an actual Project Lead or manager-of-record relationship grants visibility, a distinction the governing Phase 18 instructions made explicit. Review authority (submit for decision) is the creator's current Manager, the linked Project's Project Lead, or Administrator — never the creator, defensively guarded exactly like `LeaveRequestController::authorizeDecisionAuthority()`. Draft-management authority (edit/delete/attachment mutation/submit/return-to-draft) is creator-or-Administrator only — participants gain visibility but never workflow-management authority. This phase also introduces the first genuine file-upload authorization surface: an attachment's access always inherits its parent Service Report's own visibility (whoever may view the report may download its attachments), while upload/removal is further restricted to the creator/Administrator and only while the report is `draft`.
  - **Implemented as of Phase 19 (DEC-042):** **no new permission at all** — the illustrative `incident.create`/`incident.assign`/`incident.resolve` catalog in `01_PRODUCT_REQUIREMENTS.md` §3 is explicitly non-authoritative (it predates every real permission this codebase has actually built). `App\Http\Controllers\Api\V1\IncidentReports\Concerns\AuthorizesIncidentReportAccess` resolves visibility entirely in-controller: an Incident Report is visible to its reporter, its assigned investigator, its participants, the reporter's *current* direct Manager (`Staff.manager_id`, a plain relationship check), or Administrator. **Deliberately narrower than Service Reports (DEC-041), which itself was already narrower than Schedule Entries:** a linked Project's Project Lead gains **no** visibility or authority here at all, even via the established `ProjectMembership` check Service Reports reuses — an explicit product-owner instruction, not an oversight. Assignment authority (assign/reassign, and any assignment bundled into start-investigation) is the reporter's current Manager or Administrator only — never the reporter, never the assignee themselves. Content-management authority is status-dependent: while `reported`, the reporter themselves additionally qualifies alongside the assigned investigator/manager-of-record/Administrator; once `under_investigation`, the reporter alone no longer suffices. Resolve/close/reopen authority is the assigned investigator, the reporter's current Manager, or Administrator. Deletion authority (reporter or Administrator only) is further gated to a report still `reported` and unassigned — once assigned or investigated, deletion is blocked for everyone, Administrator included; resolution/closure are the only paths forward. The second genuine file-upload authorization surface (after Service Reports): an Incident Report attachment's access inherits its parent's own (narrower) visibility, while upload/removal require both a content-mutable status (`reported`/`under_investigation`) and the same content-management authority that gates the report's own content.
- **Data isolation is deliberate**, not implicit: e.g. a Supervisor's visibility into staff records, work logs, or leave requests must be explicitly scoped (own team vs. everyone) at the query/policy level, not just hidden in the UI. Server-side enforcement is mandatory; the UI hiding a button is never sufficient. **Implemented as of Phase 9:** the first real instance of this principle — `location.view` is necessary but not sufficient for a Manager; `CheckInController::authorizeViewingLocationOf()` additionally checks `$target->manager_id === $requesterStaff->id` before returning another staff member's check-in history, entirely at the query/controller level, never merely hidden client-side. **Implemented as of Phase 10 (DEC-033):** a second, differently-shaped instance — Phase 9 scoped a *permission holder* (Manager) to a subset of records; Phase 10 instead scopes a requester who holds **no relevant permission at all**. `App\Http\Controllers\Api\V1\Projects\Concerns\AuthorizesProjectVisibility` (shared by `ProjectController`/`ProjectMembershipController`) checks `projects.view` first (Administrator/Manager, unscoped); absent that, it checks whether the requester's linked Staff record holds a Project Membership on the specific Project being viewed, and denies (`403`) otherwise. This is applied directly to `GET /api/v1/projects`/`{public_id}` (not a separate `/me/projects` route) — the first case in this codebase where a primary resource's own list/show endpoints are not gated by a single `can:<permission>` route middleware. **Implemented as of Phase 11 (DEC-034):** `App\Http\Controllers\Api\V1\Tasks\Concerns\AuthorizesTaskAccess` extends the same shape to Tasks (a linked-Staff requester sees Tasks in Projects they belong to, plus any Task assigned to them directly — never broader than the equivalent Project's own visibility) **and, for the first time, to writes**: `POST`/`PUT`/`PATCH /api/v1/tasks` carry no `can:<permission>` route middleware at all, with Project Lead/assignee authority resolved entirely inside the controller. **Implemented as of Phase 12 (DEC-035):** a third, narrower shape — Work Log visibility deliberately does **not** extend Project/Task visibility. Project membership never grants visibility into another member's logged work merely by association: an ordinary Staff member sees only their own Work Logs (`/me/work-logs`); a Manager is scoped to direct reports only (not company-wide, unlike `tasks.view`/`projects.view`); a Project Lead gets read-only visibility into their led Projects' Work Logs and no write authority at all. `GET /api/v1/work-logs`/`{public_id}` carry no `can:<permission>` middleware (scoped in-controller, `AuthorizesWorkLogVisibility`); writes are a conventional `can:work-logs.manage` route (Administrator-only) — the read/write split is opposite Phase 11's (there, writes were also scoped in-controller; here, only reads are, because Work Logs get no equivalent of Project Lead/assignee *write* authority at all). **Implemented as of Phase 13 (DEC-036):** a fourth shape — Leave Request visibility mirrors Phase 12's Manager-scoped shape (no Project-Lead-equivalent tier; Leave is an HR domain, not a Project domain, so Project membership grants no Leave visibility whatsoever), but extends row-level scoping to a genuine **two-party approval decision** for the first time: `LeaveRequestController::authorizeDecisionAuthority()` grants approve/reject authority to Administrator or the requester's *current* direct Manager only, explicitly denying the requester themselves even if the relationship were somehow satisfied (defense in depth alongside `Staff::wouldCreateCycleWith()`'s structural prevention). `POST .../approve`/`reject` carry no `can:<permission>` route middleware at all. **Implemented as of Phase 14 (DEC-037):** a fifth, structurally different shape — not a permission-holder scoped to a subset of records (Phases 9/12/13) or a membership check against no permission at all (Phases 10/11), but a **per-employee audience match** against broadcast content every eligible employee is equally entitled to see in full: `App\Http\Controllers\Api\V1\Announcements\Concerns\ScopesAnnouncementVisibility` returns only `published` Announcements that are `company_wide`, or `scoped` to a Department/Team the requester's linked Staff record currently belongs to (union, evaluated at read time). This governs `/api/v1/me/announcements` only — the management surface (`/api/v1/announcements`) is instead a conventional `can:announcements.manage` permission gate with no row-level scoping at all, since it has exactly one authorized actor type (Administrator). **Implemented as of Phase 15 (DEC-038):** a sixth, simpler shape — plain per-row ownership with no group/membership/permission dimension at all: `NotificationController::authorizeOwnership()` denies (`404`) any request for a Notification whose `recipient_user_id` doesn't match the authenticated User's own id. There is no "everyone in a group sees this" case (unlike Phase 14's audience match) and no permission-holder tier that sees more than its own rows (unlike every other module) — not even Administrator can read another User's notification through this API. **Implemented as of Phase 16 (DEC-039):** a seventh shape, combining Phase 15's "no Administrator override" absoluteness with genuine multi-party membership for the first time — `AuthorizesConversationAccess::authorizeMembership()` denies (`404`) any request for a conversation/its messages unless the requester's own linked Staff record currently appears in `conversation_members`. Unlike Phase 15's single-recipient ownership, a conversation can have two (direct) or many (group/project) legitimate viewers at once, but the *mechanism* is identical in spirit: a plain existence check with no permission or role dimension, and no actor — Administrator included — sees more than their own memberships. **Implemented as of Phase 17 (DEC-040):** an eighth shape, the first to compose two already-established rules rather than introduce a new one — Schedule Entry visibility is creator-or-participant-or-Project-visible (reusing Phase 10's `AuthorizesProjectVisibility` rule verbatim for the Project-linked case, never re-derived), and Project Milestone visibility reuses that same rule outright with no modification at all. **A Manager gains no automatic visibility into a direct report's private (non-Project-linked) Schedule Entry merely from the manager relationship** — a deliberate, explicit departure from Phase 12/13's Manager-of-direct-reports scoping (Work Logs/Leave), reflecting that a personal calendar entry is treated as more sensitive than logged work duration or a leave reason. The unified `GET /api/v1/schedule` aggregation is the first endpoint in this codebase to apply four *different* row-level visibility rules within a single response, one per source item, rather than one rule per endpoint — each item is included or excluded exactly as if the requester had called that source's own dedicated endpoint. **Implemented as of Phase 18 (DEC-041):** a ninth shape, composing three already-established rules (manager-of-record from Leave/Work Logs, Project Lead from Tasks/Schedule Entries, and plain creator/participant ownership) while **deliberately declining to compose a fourth** — Schedule Entries' "Manager holding `projects.view` sees every Project-linked item regardless of membership" carve-out is *not* replicated for Service Reports, per the explicit product-owner instruction against a broad `service-reports.view` permission. `App\Http\Controllers\Api\V1\ServiceReports\Concerns\AuthorizesServiceReportAccess::scopeVisibleServiceReports()` is the query-scoping counterpart, applied to `GET /api/v1/service-reports` itself (no bare `can:` middleware, mirroring every prior row-level-scoped index). **Implemented as of Phase 19 (DEC-042):** a tenth shape, composing only three of Service Reports' four rules — reporter (creator-equivalent), participant, and manager-of-record — while **deliberately declining to compose the fourth**: Incident Reports' `App\Http\Controllers\Api\V1\IncidentReports\Concerns\AuthorizesIncidentReportAccess` grants **no** Project-Lead visibility at all, even though many Incident Reports are Project-linked, per an explicit product-owner instruction that incident subject matter (safety/security/property events) is treated as more sensitive than Service Reports' routine client-work documentation — narrower than every prior row-level shape in this codebase, Service Reports included. It also adds a new dimension no prior shape has needed: visibility alone is not enough to edit — `canManageContent()` additionally depends on the report's own `status` (`reported` admits the reporter themselves as an editor; `under_investigation` does not, narrowing to the assigned investigator/manager-of-record/Administrator) and is further gated by a separate `status->isContentMutable()` check that blocks all editing once `resolved`/`closed`, restorable only via an explicit `reopen` action. Assignment authority (who may populate/change `assigned_to_staff_id`) is a fifth, narrower predicate still — reporter's manager-of-record or Administrator only, deliberately excluding the assignee themselves (no self-reassignment) and the reporter (who reports an incident but never assigns their own investigator).

## Least Privilege

- Default-deny: new permissions/endpoints are inaccessible until explicitly granted to a role.
- Super Administrator access is expected to be rare and itself auditable (see Audit Logging).

## Account States

- **Implemented (Phase 4):** `users.status` is one of `active`, `suspended`, `inactive` (`App\Enums\AccountStatus`) — distinguishing "temporarily blocked" from "no longer employed" is deferred to whenever a real offboarding workflow is designed; for now `inactive` and `suspended` both simply block authentication identically.
- Active may authenticate normally. Suspended and inactive may not start a new session/token — enforced explicitly in `AuthController::login` (API) and `LoginForm::login` (Admin), returning a generic-but-honest message rather than a raw 500 or misleading "invalid credentials."
- **A suspended/inactive account also loses already-authenticated access**, not just the ability to log in again: a single `App\Http\Middleware\EnsureAccountIsActive` (alias `account.active`) is applied to `GET /api/v1/auth/me` and the Admin `/home` placeholder. For the API it revokes the current Sanctum token and returns `403`; for the Admin session it logs the user out and redirects to `/login`. Deliberately not applied to either surface's logout route — revoking one's own access is always allowed.
- This is centralized in one middleware plus `User::isActive()`, not scattered per-controller checks (CLAUDE.md §7).

## Administrative Access

- Administrative actions (staff suspension, role changes, settings changes, data exports) are higher-risk and are candidates for stricter checks (e.g. requiring a specific elevated permission, and always audit-logged). **Implemented as of Phase 21:** data exports (every Phase 20 report export, and the Audit Log's own export) and every Staff/Organization/Client/Project/Task/Announcement/attachment mutation named in DEC-044's event catalog are audit-logged. **Staff suspension and role changes are not yet audited** — no mutation endpoint exists anywhere in the application for either (`users.status`/`users.role_id` can currently only be set at account creation); this is a documented, pre-existing gap the Phase 21 consistency audit surfaced, not something this phase's own scope authorized it to fix by building new User-management endpoints. See DEC-044's Known Limitation.
- **Implemented as of Phase 5 (DEC-028), retiring the Phase 4 transitional `is_admin` flag (DEC-024):** the Admin Backoffice's access chain is `auth` → `account.active` → `can:admin.access` → `/home` (`routes/web.php`), enforced both at login (`App\Livewire\Auth\LoginForm`) and on every subsequent request to `/home` via Laravel's built-in `can` route middleware — not a one-time login-only check. `is_admin` no longer exists on `users`; there is no remaining reference to it in application authorization logic.

## API Access

- The API is the enforcement boundary (see `04_API_CONVENTIONS.md`) — every endpoint independently authorizes, regardless of what the calling client (mobile/admin) already filtered client-side.
- **Implemented as of Phase 5:** `UserResource` exposes a stable `role` field (the role's *name*, e.g. `"administrator"` — never the internal numeric `role_id`) for legitimate future mobile UI use (e.g. role-aware navigation).
- **Implemented as of Phase 6:** the first permission-gated endpoints — `/api/v1/departments`, `/teams`, `/positions` — via `Route::middleware(['auth:sanctum', 'account.active', 'can:organization.view'])` (reads) and `can:organization.manage` (writes), exactly the pattern Phase 5 anticipated. `Department`/`Team`/`Position` resources and route model bindings expose/accept only `public_id`, never an internal numeric id — including a client-supplied `department_id`, which is resolved server-side from the submitted public ULID.
- **Implemented as of Phase 7:** `/api/v1/staff` follows the identical `can:staff.view`/`can:staff.manage` pattern. `StaffResource` additionally demonstrates a within-resource sensitivity split: every `staff.view` holder sees the full Staff Directory shape (name, contact, department/team/position, manager, status, and a plain `has_user_account` boolean), but the linked `User`'s own identity (`public_id`/email/account status) is only included when the requester also holds `staff.manage` (`$this->when($request->user()?->can('staff.manage'), ...)` in the resource) — Staff Directory data and staff-management data are kept genuinely separate, not merely documented as separate.
- **Implemented as of Phase 8:** `/api/v1/clients` and `/api/v1/contacts` follow the identical `can:clients.view`/`can:clients.manage` pattern (both resources share the same permission pair — Contact has no independent authorization surface). No within-resource sensitivity split was needed here (unlike Staff's `User` linkage) — Client/Contact records carry no more-sensitive nested identity to gate.
- **Implemented as of Phase 9:** self-service (`/api/v1/me/status`, `/api/v1/me/check-ins`) requires no permission at all beyond `auth:sanctum`/`account.active` — only that the authenticated `User` has a linked `Staff` record, checked in the controller (`403`, `no_linked_staff_record`) rather than via the permission system, mirroring `GET /api/v1/auth/me`. Viewing another staff member's data uses two different sensitivity levels for the first time in one phase: `can:staff-status.view` alone gates status (Administrator/Manager/Staff), while `can:location.view` only gates *whether a Manager may view anyone's* check-ins — *whose* they may view is enforced separately inside `CheckInController`, scoped to direct reports. `StaffResource` gained `operational_status` (safe, since its grantees mirror `staff-status.view`'s) but no location field of any kind.
- **Implemented as of Phase 10:** `/api/v1/projects` and `/api/v1/projects/{public_id}` (and its nested `/members`) deliberately carry no `can:` route middleware on their `GET` routes — permission-holders (`projects.view`: Administrator/Manager) and Staff-linked non-holders (scoped to their own Project Memberships) are both legitimate requesters of the *same* endpoints, just with different result sets, so a bare permission middleware couldn't express this without either over-granting or blanket-denying Staff. Writes (`POST`/`PUT`/`PATCH`/`DELETE`, on both Projects and Project Memberships) remain conventionally gated by `can:projects.manage` route middleware, same as every prior module.
- **Implemented as of Phase 11:** `/api/v1/tasks` goes one step further than Phase 10 — `GET`, `POST`, and `PUT`/`PATCH` all carry **no** `can:<permission>` route middleware. `tasks.view`/`tasks.manage` holders, a Project Lead scoped to their own Project, and a Task's assignee (status-only) are all legitimate requesters of the same write endpoints with different field/scope limits, which a bare permission middleware cannot express. `DELETE /api/v1/tasks/{public_id}` is the exception — it remains a conventional `can:tasks.manage` route (Administrator-only), further narrowed in-controller to Tasks still in their initial `todo` status.
- **Implemented as of Phase 12:** two genuinely separate endpoint families, not a single scoped one. `/api/v1/me/work-logs` (self-service: list/create/edit/delete own) needs no permission at all — only a linked Staff record (and, for creation, `active` employment status) — mirroring Phase 9's domain-check pattern; the performer identity is always server-derived, never a client-supplied `staff_id`. `/api/v1/work-logs` (supervisory/administrative) has its `GET`/index/show scoped in-controller with no `can:` middleware (Administrator sees all; Manager, holding `work-logs.view`, sees only their own direct reports; a Project Lead sees, read-only, Work Logs in Projects they lead) — but unlike Phase 11's Tasks, **writes here are a plain `can:work-logs.manage` route** (Administrator-only): no Project Lead or Manager write authority was introduced for Work Logs at all, a deliberately stricter posture than Tasks since Work Logs are historical records.
- **Implemented as of Phase 13:** `/api/v1/leave-types` follows the identical `can:leave-types.view`/`can:leave-types.manage` pattern as every prior master-data resource. `/api/v1/me/leave-requests`/`/me/leave-balances` need no permission at all — only a linked Staff record (and, for creation, `active` employment status) — mirroring Phase 9/12's domain-check pattern; a `public_id` belonging to another Staff member returns `404`, not `403`. `/api/v1/leave-requests` (supervisory) has `GET`/index/show scoped in-controller with no `can:` middleware (Administrator sees all; Manager, holding `leave-requests.view`, sees only direct reports); `POST`/cancel require `can:leave-requests.manage` (Administrator-only); `POST .../approve`/`reject` carry **no** `can:` middleware at all — the first explicit two-party approval workflow in this codebase, with authority resolved entirely in-controller rather than via a route-level permission gate, since "may this Manager decide this specific request" cannot be expressed as a bare permission check.
- **Implemented as of Phase 14:** `/api/v1/me/announcements` needs no permission at all — only a linked Staff record — mirroring Phase 9/12/13's domain-check pattern; a `public_id` outside the requester's audience (draft, archived, or a different Department/Team) returns `404`, not `403`, since its existence is itself sensitive. `/api/v1/announcements` (management) is gated end-to-end by a single `can:announcements.manage` route middleware — reads included, unlike every prior module's supervisory surface — since there is exactly one authorized actor type (Administrator) and no scoped-visibility case to express. `POST .../publish`/`archive` sit inside the same `can:announcements.manage` group (not permission-less like Leave's approve/reject) because there is no second, row-level-scoped authority to resolve — only Administrator may ever call them.
- **Implemented as of Phase 15:** `/api/v1/me/notifications...` needs no permission at all (no `notifications.view`/`.manage` was defined), and — for the first time among every `/me/...` surface — no linked Staff record either: recipient identity is the `User` account itself (DEC-038), so ownership is checked directly against `recipient_user_id`, not through a Staff relationship. A `public_id` belonging to another User returns `404`, not `403`. There is no supervisory/management surface at all — no route, permission, or Admin UI lets anyone read or write another User's notifications, including Administrator; Notifications are produced only by internal application code (currently `AnnouncementController::publish()`'s audience fan-out).
- **Implemented as of Phase 16:** `/api/v1/conversations...` needs a linked Staff record (unlike Phase 15, reverting to every earlier `/me/...` surface's precedent) but no permission at all. Unlike every prior module, `GET /conversations` is itself the self-scoped list — there is no separate `/me/conversations` and no broader supervisory `/conversations` a permission-holder sees more of; the same endpoint, for every caller, returns only conversations the caller's own linked Staff record currently belongs to. A `public_id` outside the requester's current membership returns `404`, not `403`, for anyone, Administrator included. Group conversation membership management (`POST`/`DELETE .../members...`) is owner-only, checked in `ConversationMemberController`, not via a permission. Project conversation access (`POST /projects/{public_id}/conversation`) requires current Project Membership specifically — `projects.view` (Administrator/Manager) grants no bypass, a deliberate divergence from how Project visibility itself works (Phase 10).
- **Implemented as of Phase 17:** `/api/v1/schedule-entries...` needs a linked Staff record to create (the creator identity is always server-derived) but no permission at all — visibility/authority are resolved entirely in-controller (`AuthorizesScheduleEntryAccess`). A `public_id` the requester cannot view at all (not creator, not participant, not visible via a linked Project) returns `404`, not `403`; one they can view but not edit (a mere participant) returns `403` on write attempts. `/api/v1/projects/{project}/milestones...` requires the same visibility as the Project itself (`projects.view` or current membership); writes require `projects.manage` or the Project's own Project Lead — no new permission. `GET /api/v1/schedule` needs no permission of its own at all — each aggregated item is included only if the requester could already see it through that item's own source endpoint (Task/Leave/Milestone/Schedule Entry), so this endpoint can never leak data its four constituent endpoints wouldn't already show the same caller.
- **Implemented as of Phase 18:** `/api/v1/service-reports...` needs a linked, active Staff record to self-create (the creator identity is server-derived unless Administrator explicitly names another Staff member) but no permission at all — visibility/authority are resolved entirely in-controller (`AuthorizesServiceReportAccess`). A `public_id` the requester cannot view at all returns `404`; one they can view but not manage (a mere participant, or a reviewer attempting a draft-only action) returns `403`. Workflow transitions are exclusively explicit action endpoints (`/submit`, `/review`, `/reject`, `/return-to-draft`) — there is no generic status `PATCH`, and each aborts `409` for any status other than its own required starting state. Attachment endpoints (`POST/.../attachments`, `GET .../attachments/{public_id}/download`, `DELETE .../attachments/{public_id}`) need no permission of their own — download authorization is always exactly the parent report's own `authorizeView()`, and upload/removal additionally require both draft status and creator/Administrator identity.
- **Implemented as of Phase 19:** `/api/v1/incident-reports...` needs a linked, active Staff record to self-create (the reporter identity is server-derived unless Administrator explicitly names another Staff member via `reporter_staff_id`) but no permission at all — visibility/authority are resolved entirely in-controller (`AuthorizesIncidentReportAccess`). A `public_id` the requester cannot view at all returns `404`; one they can view but not manage (a mere participant, an unassigned/unrelated reporter attempting an investigator-only action) returns `403`. Workflow transitions and assignment changes are exclusively explicit action endpoints (`/assign`, `/reassign`, `/start-investigation`, `/resolve`, `/close`, `/reopen`) — there is no generic status `PATCH`, `assigned_to_staff_id` is never accepted by the generic `PUT`/`PATCH`, and each action aborts `409` for any status other than its own required starting state. `/assign` aborts `409` if already assigned (use `/reassign`); `/reassign` aborts `409` if not yet assigned (use `/assign`). Attachment endpoints mirror Service Reports' shape exactly, but gated by `status->isContentMutable()` (`reported`/`under_investigation`) instead of a single `draft` state, and by the same status-dependent content-management authority (not a flat creator-or-Administrator rule) that governs the report's own content.
- Tokens scoped appropriately per client type where the auth mechanism supports it (e.g. Sanctum token abilities), to limit blast radius of a leaked mobile token vs. an admin session — no token abilities are defined yet (single mobile client type; revisit if a second API-consuming client type is added). **Implemented as of Phase 22 (Security Audit, F-02):** tokens now bound in *time* even though not yet in *ability* — `config('sanctum.expiration')` (30 days) closes the "leaked token never expires" half of this gap; ability scoping remains correctly deferred until a second client type actually exists.
- **`GET /api/v1/health` (Phase 3) and `POST /api/v1/auth/login` (Phase 4) are the deliberate public exceptions** — health returns only `{status, timestamp}`; login is otherwise unauthenticated by necessity but rate-limited and returns a generic failure message that never confirms or denies whether a given email is registered. Any future unauthenticated endpoint must be an equally deliberate, narrow, documented exception — not a default.
- `POST /api/v1/auth/logout` revokes only the token used for the request (`$request->user()->currentAccessToken()->delete()`), not every device's token — a deliberate choice leaving room for future multi-device use without inventing a session-management UI in this phase.

## Input Validation

- All input validated server-side via Form Requests (see `04_API_CONVENTIONS.md`) — never trust client-side validation alone.
- Standard Laravel protections (mass-assignment protection via `$fillable`/`$guarded`, parameterized queries via Eloquent/query builder) are the baseline; no raw SQL string interpolation.

## File Uploads

- Validate file type, size, and (where feasible) content — not just extension — before storage.
- Store uploads outside the public webroot by default, serving via authenticated/authorized routes rather than direct public URLs, unless a specific attachment type is deliberately public (e.g. a public announcement image) — decided per use case, not by default.
- Antivirus/malware scanning is a **future consideration**, not a V1 commitment — note this honestly rather than implying it exists.
- **Implemented as of Phase 18 (DEC-041):** the first real file-upload capability in this application, for Service Report attachments. Files are validated against a conservative allowlist (JPEG/PNG/PDF, `config('attachments.allowed_extensions')`) and a 10 MB size cap (`config('attachments.max_size_kb')`) via Laravel's content-sniffing `mimes` rule (not merely the client-supplied extension or `Content-Type` header). Stored on a private disk (`config('attachments.disk')`, defaulting to Laravel's `local` disk — `storage_path('app/private')`, never web-served) under a generated, randomized filename (`App\Services\Attachments\AttachmentStorage`) — an uploaded file's original name is preserved only as display metadata on the `attachments` row, never trusted as, or used to derive, the physical storage path. Every download passes through an authenticated, authorized application route (`ServiceReportAttachmentController::download()`), never a public URL — no attachment type is public in V1. Antivirus/malware scanning remains the same documented future consideration this section has always named, not newly built here.
- **Implemented as of Phase 22 (Security Audit, F-07):** the `local` disk's Laravel-13-default `'serve' => true` (`config/filesystems.php`) — which registers a framework-level signed-URL route for that disk — is now explicitly `false`. Nothing in this application ever called `Storage::url()`/`temporaryUrl()` for attachments (every download already goes through the authenticated/authorized controller routes above), so this closes a dormant, unused route rather than changing any actual behavior.
- **Implemented as of Phase 19 (DEC-042):** Incident Reports is the second consumer of the same file-upload infrastructure, reusing every control above unchanged (same allowlist, size cap, private disk, randomized filename, authenticated download route via `IncidentReportAttachmentController::download()`) — no new upload mechanism, allowlist, or size limit was introduced. Antivirus/malware scanning remains the same unbuilt future consideration.

## Sensitive Information

- PII (staff personal details, leave reasons, incident details) is handled with the same permission-scoping discipline as any other data — visibility is permission-gated, not "logged-in users can see everything."
- **Implemented as of Phase 13:** Leave Request `reason` text and approval/rejection/cancellation `note`s are visible only to the requester, their current direct Manager, and Administrator — never company-wide, and never inferable from Project/Task/Client data (Leave is a standalone HR domain with no cross-module coupling, per DEC-036's Critical Domain Boundary).
- **Implemented as of Phase 14:** an Announcement's content is, by design, visible to every employee in its audience (that is the point of a broadcast channel) — the sensitivity concern here is instead ensuring a `draft`/`archived` announcement, or one scoped outside a Staff member's Department/Team, is never leaked (see Data isolation above). Per-staff acknowledgement state is private: a coworker's acknowledgement is never exposed to another Staff member, and the management surface exposes only an aggregate `acknowledgements_count`, never a per-staff list (per DEC-037's explicit rejection of an engagement/read-rate dashboard).
- **Implemented as of Phase 15:** Notification `title`/`message` text is deliberately generic and never carries a sensitive domain detail — the one wired producer (Announcement publish) sets `title` to the Announcement's own title (already non-sensitive broadcast content, equally visible via `/me/announcements`) and a fixed, generic `message` ("A new company announcement has been published."), never the Announcement body. A Notification's `source` exposes only a bounded `{type, public_id}` pair, never the source record's own content — a client follows it to the source's own, separately-authorized endpoint, which enforces its own current authorization rules independently (a Notification may remain visible after its source becomes inaccessible — see `03_DATABASE_MODEL.md`'s snapshot note; this is an accepted, documented gap, not a bypass, since no sensitive content ever lived in the Notification row itself).
- **Implemented as of Phase 16:** Message `body` content is visible only to a conversation's current members (see Messaging Privacy below and Data isolation above) — never company-wide, never inferable via any other module, and never surfaced in Notification content: the Message-received Notification's `title`/`message` are fixed and generic regardless of conversation type, never the message body, sender name, or conversation/group/project name (mirroring Phase 15's identical "notification carries a pointer, not content" precedent). A Notification's `source` for a message points only at the conversation (`{type: "conversation", public_id}`), never the message itself.
- **Implemented as of Phase 7:** Staff records deliberately collect only company-directory-level personal data (name, company contact info, employment dates/status, org placement) — no government/tax IDs, bank details, salary, medical information, or emergency contacts, all of which belong to a future, more tightly-scoped HR/personnel-record module if ever built.
- **Implemented as of Phase 8:** Client/Contact records collect only ordinary business-contact information (name, title, business email/phone, business address) — no row-level ownership/account-manager ACLs (every `clients.view` holder sees every Client/Contact, per the governing Phase 8 instructions) and no interaction-history/activity-timeline data (deferred to a future CRM-style phase if ever built).
- Avoid storing sensitive data in **logs**; be deliberate about what audit log entries capture (metadata about the change, not necessarily full sensitive payloads).

## Audit Logging

- **Implemented as of Phase 21 (DEC-009/DEC-044):** a general, project-wide `audit_logs` table plus `App\Services\Audit\AuditLogger`, capturing actor, stable action name, entity type/public-ID reference, curated changed-field names, curated allowlisted before/after values, IP address, user agent, and source (`api`/`admin`) for a deliberately curated V1 event catalog — see `docs/DECISIONS.md` DEC-044 for the full list and its explicit exclusions.
- Structurally separate from every domain-specific history table (`leave_request_actions`/`service_report_actions`/`incident_report_actions`) — those remain the sole authoritative record for their own business workflow; the general Audit Log never replaces or weakens them, and V1 deliberately does not duplicate the workflow-transition events they already capture.
- **Redaction is enforced, not merely intended:** `before`/`after` are populated only from an explicit, per-integration-site allowlist of low-sensitivity structural values (status, a public-ID reference, a role) — never a full model snapshot or raw request payload. Passwords/hashes, tokens/credentials, Leave Request reasons, Incident Report narrative fields, Service Report narrative content, Message bodies, and attachment contents/filenames are never captured.
- **Audit logs themselves are Administrator-readable only** — enforced by a direct `hasRole(Role::ADMINISTRATOR)` check (`AuthorizesAuditLogAccess`), not a new permission; Manager and Staff have no access at all, via `GET /api/v1/audit-logs`/`/export`. Not general staff-visible, and (unlike several other supervisory surfaces in this codebase) not Manager-visible either — there is no Manager-of-direct-reports tier for Audit Log access.
- Append-only: no create/update/delete endpoint exists for an individual entry, not even for Administrator.
- Synchronous, transactional writes only — no queue/Redis/background processing (see `02_ARCHITECTURE.md` §6's identical reasoning for Notifications/Messaging, now extended to Audit Logging at the same ~100-employee scale).

## Location Data

- V1 favors **explicit check-ins**, not continuous location tracking (DEC-005). This is both a product and a privacy stance — staff location data is only captured at deliberate check-in moments.
- **Implemented as of Phase 9 (DEC-032):** `staff_checkins` (`latitude`/`longitude`, `decimal(10,7)`, plus optional `accuracy_meters`/`location_label`/`note`) is populated only by the checking-in staff member themselves (`POST /api/v1/me/check-ins`) — no background/continuous/periodic collection exists anywhere in the codebase. Visibility is scoped, not company-wide: ordinary Staff can only ever see their own location (via `/me/check-ins`); a Manager sees only their own direct reports' check-ins (`location.view`, further scoped by `Staff.manager_id` — see Authorization above); an Administrator sees everyone's. Check-ins are immutable except for Administrator deletion (`location.manage`) — no ordinary user can edit or delete their own historical check-in. At ~100 employees and explicit, user-triggered events (not periodic telemetry), a normal indexed relational table is sufficient — no specialized time-series database or retention-policy engine was introduced; a future phase should revisit retention (e.g. an age-based purge) if check-in volume ever grows unbounded.
- **Attendance/timekeeping separation:** a location check-in is explicitly **not** a clock-in, attendance record, present-for-payroll signal, or timesheet entry — and the absence of a check-in is likewise **not** absence, lateness, or off-work. Neither this phase's code nor any later phase should infer attendance/payroll/timekeeping facts from `staff_checkins` without a deliberate, separately authorized module built for that purpose.
- **Leave separation:** `App\Enums\OperationalStatus::OffDuty` is an operational-visibility signal only ("I'm not currently working") — it is not a leave request, approval, or balance, and carries no relationship to a future Leave Management module's data.

## Messaging Privacy

- **Implemented as of Phase 16 (DEC-039):** direct and group conversations/messages are visible only to their current participants; project conversations are visible only to current Project members. This is now real, tested code, not merely a stated intention: `App\Http\Controllers\Api\V1\Messaging\Concerns\AuthorizesConversationAccess` never calls `$user->can(...)`, so there is **no general "admin can read all messages" default** — Administrator's centralized `Gate::before` override is never invoked for any Messaging endpoint, and a conversation/message outside the requester's own current membership is `404` for Administrator exactly as it is for anyone else. No administrative/investigation capability of any kind was built in V1 — per this section's own original guidance, that remains a deliberate future decision (requiring its own permission and, ideally, real audit logging — the general Audit Log itself is implemented as of Phase 21, but Messaging deliberately was not retrofitted into it, since doing so would be exactly the kind of speculative, undemonstrated-need capability this section has always guarded against; a genuine Messaging moderation/investigation feature remains a separate, future, explicitly-scoped decision) rather than an incidental side effect of admin access elsewhere, or something built speculatively now.

## Scheduler Privacy

- **Implemented as of Phase 17 (DEC-040):** a manually created Schedule Entry is private by default — visible only to its creator, its participants, and (if it is linked to a Project) whoever can already see that Project. **A Manager holds no special visibility into a direct report's private Schedule Entries** merely from the manager relationship — a deliberate, explicit product-owner decision distinguishing Schedule Entries from Work Logs (`work-logs.view`) and Leave Requests (`leave-requests.view`), both of which do grant a Manager visibility into their direct reports' records. Administrator retains full visibility/management over every Schedule Entry (unlike Messaging/Notifications' deliberate no-override design) — this is a documented, intentional difference between modules, not an inconsistency. The unified `GET /api/v1/schedule` endpoint never widens any source's own visibility: an item appears in the aggregation if and only if the requester could already see it through that source's own dedicated endpoint (`/schedule-entries`, `/tasks`, `/me/leave-requests` or `/leave-requests`, `/projects/{project}/milestones`).

## Incident Report Privacy

- **Implemented as of Phase 19 (DEC-042):** an Incident Report is private by default — visible only to its reporter, its assigned investigator, its participants, and the reporter's *current* direct Manager. **Unlike every other Project-linkable module in this codebase (Service Reports, Schedule Entries, Tasks), a linked Project's Project Lead gains no visibility into an Incident Report at all**, even though the same `ProjectMembership`/`ProjectLead` check is readily available and reused elsewhere — a deliberate, explicit product-owner decision that incident subject matter (workplace safety, IT/security, property/equipment events) warrants a narrower default audience than routine Project-linked work. Administrator retains full visibility/management over every Incident Report. No per-record confidentiality flag, HR/harassment/whistleblower workflow, or medical/injury-record handling was built — V1's privacy stance is expressed entirely through this narrow, structural visibility rule, not a configurable sensitivity level; a genuinely confidential-case requirement is a future, separately-scoped decision, not something this phase quietly grew into.

## Rate Limiting

- **Implemented (Phase 4):** both login surfaces are limited to 5 attempts per minute, keyed by `email|ip` (a single named `login` limiter, `App\Providers\AppServiceProvider::boot()`), so one abusive client can't lock out another legitimate user of the same account. The API route (`POST /api/v1/auth/login`) uses the `throttle:login` route middleware; the Admin Livewire component enforces the same limiter directly in `LoginForm::login()` (a route-level `throttle` middleware would not see Livewire's internal AJAX update requests). Exceeding the limit returns `429 Too Many Attempts` (API) or a form validation error (Admin).
- Thresholds for future write-heavy or abuse-prone endpoints remain to be tuned per endpoint when a real need is demonstrated, not decided in the abstract here. **Phase 16 (Messaging) did not introduce endpoint-specific rate limiting** — message-send volume at ~100 employees was not judged to demonstrate a need for one yet; this should be revisited if real usage shows otherwise, consistent with this document's general "don't build ahead of demonstrated need" posture.

## Client-Side Token Storage

- **Implemented (Phase 4, DEC-026):** the Flutter app persists its Sanctum bearer token via `flutter_secure_storage` (iOS Keychain; Android EncryptedSharedPreferences/Keystore) — never plain `SharedPreferences`, source code, or an unencrypted file.

## Secrets & Configuration

- Secrets live in environment configuration (`.env`, or a proper secrets manager in production), never committed to the repository.
- Environment-specific config (API keys, DB credentials, mail/queue credentials) follows standard Laravel config practice — no hardcoded credentials in code at any point.

## Production Environment Separation

- Distinct configuration and credentials per environment (local/staging/production) — non-negotiable before any real deployment.
- **Implemented as of Phase 24 (repository side; DEC-047):** a staging environment is now genuinely distinct from local development at the configuration-mechanism level, not merely by convention. Local dev's `docker-compose.yml`/`.env.docker.example` remain entirely unchanged; staging uses its own dedicated `docker-compose.staging.yml`, its own application image (`docker/php/Dockerfile.staging`, source baked in — no bind-mounted host files), and its own `apps/api/.env`/`.env.staging` pair, created fresh on the staging host from committed, placeholder-only `.example` templates — never copied from a developer's local `.env`. Staging's `.env.staging.example` sets `APP_ENV=staging`/`APP_DEBUG=false`/`LOG_LEVEL=info` explicitly and requires unique, generated database credentials distinct from local dev's self-documented dev-only value. No production environment exists yet — this remains fully future work, per the roadmap's own phase sequencing (the Release Readiness phase — re-baselined 2026-09-22, DEC-048; see `docs/ROADMAP.md` for its current number).
- **Phase 26 Gate 1 (repository side only; DEC-050):** the staging TLS architecture is now decided and partially prepared in the repository, but **not deployed**. `docker-compose.staging.yml`'s `nginx` service is now loopback-bound (`127.0.0.1:8012`, was `8012`) — the planned host-level Nginx (extending an already-proven pattern on this shared VPS) will be the only process able to reach it once deployed. `apps/api/bootstrap/app.php` now configures `trustProxies(at: '*')` so Laravel will correctly recognize an HTTPS request forwarded through that host proxy — safe specifically because the loopback bind means no other process can ever originate a request to this application. **Still not yet true, exactly as before:** `SESSION_SECURE_COOKIE` remains `false` in the staging template until real HTTPS exists on that host *and* the trusted-proxy scheme detection is independently verified against real traffic (flipping either prematurely would silently break Admin Backoffice login) — see `docs/DEPLOYMENT_STAGING.md` §13 and `docs/phases/V1_PHASE_26_STAGING_MOBILE_CONNECTIVITY_TLS_PLAN.md` §8 for the exact gated sequence that resolves this at Gate 2.
- **Phase 26 Gate 2 (deployed and verified on staging, 2026-09-23; DEC-051):** public traffic reaches staging only via Cloudflare (proxied, SSL/TLS **Full (strict)**) → a **shared** DigitalOcean Cloud Firewall whose inbound 80/443 is restricted to Cloudflare IP ranges → the **shared** host Nginx, which terminates TLS with a publicly trusted Let's Encrypt certificate for `company-staging.storm-ark.com` and redirects HTTP → HTTPS → `127.0.0.1:8012` (loopback-only Docker publish). The firewall is shared VPS infrastructure: no change was made to it for Company App, and Company App must never weaken it (e.g. opening 80/443 to all sources) to obtain or renew a certificate. Staging now runs with `APP_DEBUG=false` and `SESSION_SECURE_COOKIE=true`; operator verification confirmed Laravel recognises the proxied request as HTTPS, session cookies carry the `Secure` attribute, and Admin login/session/logout and API token authentication work over HTTPS. The `trustProxies(at: '*')` safety argument (only a loopback listener exists) is unchanged. These are infrastructure verifications, not UAT. The real deployment-only `.env.staging` file is now also explicitly git-ignored at the repository root (defense in depth; the tracked `.env.staging.example` is unaffected).
